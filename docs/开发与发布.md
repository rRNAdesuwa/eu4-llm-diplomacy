## 源码协作

开发者通过 Git 提交、拉取和合并源码。首次在本机开发时复制 `local.env.example` 为 `local.env`，在本地填写游戏目录、用户数据目录、Python 和编译器路径；`local.env` 已被忽略，不能提交。发布包不包含本机绝对路径。

GitHub 仓库应重点保留自己编写的源码、文档、构建工具和版本元数据。运行日志、备份、存档、大型反汇编、游戏原始内容、历史构建和凭据应在上传前逐项审核。源码提交、Git 标签和 GitHub Release 附件应明确对应关系。

## 多版本 profile 与 Agent 协助

多版本支持应维护一个版本表，把每个 `eu4.exe` SHA-256 映射到成套的 RVA profile、机器码签名、DLL 文件、目标游戏版本和验收记录。加载器先计算哈希并选择 profile；没有精确匹配时拒绝加载。不同哈希不能共用旧 DLL，除非新的 RVA、签名和行为已经重新验证。

维护者可以让 Agent 在本地项目中协助：读取目标 exe 的哈希、检查现有 profile、更新 `EXPECTED_HASH` 和 `release/release.json`、生成新包及校验表。请求 Agent 时要让它先做只读检查，并区分“只换路径”和“换了二进制构建”。如果哈希不同，Agent 只能在完成新构建的 RVA/签名分析、编译和实际验收后提交兼容性修改；不能为了绕过拒绝加载而单独替换哈希字符串。

面向人工操作的日志读取和实验步骤见[《人工实验与日志读取流程》](人工实验与日志读取流程.md)。

## 每次发布

1. 修改 `work/native/authorized-probe-v9.cpp` 或相关构建脚本，并在新的游戏进程、独立实验存档中验收。当前 v9 构建入口为：

   ```powershell
   .\work\native\build-automated-diplomacy.ps1
   ```

   构建脚本从本地配置读取编译器，并构建 v9 的和平授权、固定宣战脚本和原生有效性诊断。新二进制不能直接继承旧验收结论。

2. 至少验证 v9 安装事件、固定宣战、授权自检、授权白和的 `state 0 → state 2` 以及英法战争结束。金币版本还要核对原生金额、支付方和所有收款方国库变化，再使用独立证据验证保存重载。
3. 更新版本 profile 和 `release/release.json`：递增 `version`，写入实际 DLL 文件名和 SHA-256、目标游戏哈希、对应 RVA/签名 profile、能力范围及真实验证状态。若换游戏版本或改变 action 布局，必须重新适配和验收。
4. 同步更新 `docs/DLL安装与更新.md`，明确新增请求文件、前置条件、日志事件和已知限制。保留旧版本 ZIP 和校验文件。
5. 在项目根目录运行只做文件打包的命令：

   ```powershell
   python -B .\tools\package_release.py
   ```

   打包器按 allowlist 收集 DLL、加载器、请求工具、版本依赖、元数据和文档，检查文本中是否混入本机绝对路径，生成逐文件哈希和 ZIP 哈希。不启动游戏、不编译、不注入、不自动上传；同版本 ZIP 已存在时会拒绝覆盖。
6. 审核 ZIP 内容，把源码提交到对应 Git 标签，再把 ZIP 和 `.zip.sha256` 上传到 GitHub Release。源码继续开发时不会改变已发布 ZIP；下一次验收后发布新版本。

用户的更新顺序固定为：退出游戏 → 解压完整新包 → 启动新游戏进程 → 手动加载新 DLL → 按需创建新的请求标记。不要把新 DLL 直接覆盖到旧包中，也不要在同一进程热替换。
