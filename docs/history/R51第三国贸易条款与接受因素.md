# R51：第三国贸易来源与接受因素

**记录日期：2026-10-18。** AI现在可以查询贸易条款的原生转出国候选，并选择乌得勒支向法国转移贸易竞争力。法国向英国提出这项要求时，英国原生AI拒绝；英国提供这项条款时，法国通过统一接口明确接受，战争结束，乌得勒支向法国转移50%贸易竞争力。拒绝和接受的结果均已保存，并在独立新进程核对。英国对这项要求的9项接受因素也已返回标识、中文文本和数值。

## 提议双方和条款双方分别表示什么

这里有两组容易混淆的国家角色：

- `actor`、`recipient` 和 `direction` 描述谁在什么议和上下文中提出或接收动作。例如 A 查询的上下文是 `actor=FRA`、`recipient=ENG`；`demand` 和 `offer` 是动作方向。
- `source`、`beneficiary` 描述 `transfer_trade_power` 条款的实际身份。`source` 是被转出贸易竞争力的国家，`beneficiary` 是获得该转移的国家。`UTR→FRA` 只表示贸易条款身份，不等于“UTR 发起了议和”。

因此，报告中出现的“提议 ENG→FRA”和“实际 UTR→FRA”可以同时成立：前者是议和动作的双方，后者是条款的转出国和受益国。

### A 的五次只读查询

五个 QUERY10 场景来自同一场战争上下文。它们只调用查询，执行次数为 0；`available`、`unknown` 和候选列表是查询结果，不是业务请求已提交的结果。

| 场景 | 请求中的条款身份 | 查询结果 | 说明 |
| --- | --- | --- | --- |
| 候选发现 | 未指定 `source`，预期受益国 FRA | `unknown`；候选列表完整 | 当前可发现的候选只有 `UTR→FRA`，不能把“未指定来源”误报成没有候选。 |
| `demand`，UTR 来源 | `UTR→FRA` | `available`，匹配 1 项 | 第三国来源可以作为可用候选。 |
| `demand`，默认来源 | `ENG→FRA` | `unknown` | 候选列表中没有 ENG 来源；这是缺少候选的状态，不是格式错误。 |
| `offer`，法国来源 | `FRA→ENG` | `available`，匹配 1 项 | 这次的实际条款身份与 offer 方向一致，但仍应按字段读取，不能用方向推导。 |
| `demand` + 战争赔款 | 赔款为 `ENG→FRA`；贸易条款为 `UTR→FRA` | `available`，匹配 1 项 | 组合条款分别保留各自的付款/受益和转出/受益角色。 |

## A、B、C：先修正身份，再判断拒绝

A 的执行请求明确要求 `source=UTR`、`beneficiary=FRA`，提交和原生外层回执也带着这两个身份。原生状态是拒绝，战争前后保持交战；但执行效果对象错误地写成了 `source=ENG`、`beneficiary=FRA`。生产验证器因此拒绝把这份效果当作完整结果，公共层保持 `submitted/unknown`，而不是伪造一个成功或完整的拒绝效果。A 做了各一次 execute 和 publish，不能称为业务成功。

B 使用修正后的效果身份重新取得了一份真实拒绝回执：原生状态仍为拒绝，战争继续，`source=UTR`、`beneficiary=FRA`，转移关系前后均不存在，金额为 `0/1000`，`peace_treaty=false`。这次 17 项检查通过，公共结果明确为 `rejected`。[A 错误身份报告](../../work/runtime/diplomacy-query-20261018-r51-peace-a-trade-sources/trade-source-outbound-001/report.json)和[B 修正后拒绝报告](../../work/runtime/diplomacy-query-20261018-r51-peace-b-trade-source-effects/trade-source-outbound-001/report.json)保留了外层回执与效果对象的差异。

C 没有重新提交业务请求，而是用 B 的拒绝保存结果做独立新进程读取。原生、保存流和来源报告都确认 `UTR→FRA` 的关系不存在，战争中的 FRA/ENG 对仍然存在，10 项重载检查通过。[C 重载报告](../../work/runtime/diplomacy-query-20261018-r51-peace-c-trade-rejected-reload/trade-source-rejected-reload-001/report.json)中的 `source_outcome=rejected` 和 `peace_effects.comparison.all=true` 是这项结论的依据。

这组对照说明两个判断必须分开：原生是否拒绝是一项游戏结果；效果对象是否仍忠实记录实际 `source/beneficiary` 是回执合同。A 的 `unknown` 来自后者不成立，B 才提供了可消费的完整拒绝结果。

## 哪些检查发现了问题，哪些是原生规则

- A 暴露的是效果回执的身份合同错误：外层回执是 UTR→FRA，效果对象却变成 ENG→FRA。生产验证器拒绝该对象是正确的保护行为；B 用真实拒绝结果验证了修正后的消费路径。
- A 的五场景查询暴露了候选缺失和 `unknown` 的语义边界。默认 ENG 来源缺失应保留 `unknown`，而不是格式错误；候选发现也要返回完整的 UTR 候选列表。
- D 的 `common_action_gate=false` 是真实的 ENG 外交官不可用状态。五天后 gate 恢复为 true，说明这是时间相关的原生门控，不是需要绕过的代码错误。
- value6 的固定/动态分支仍受条件控制，当前证据只足以确认本次 value6 的固定键来源，不能宣称所有情况下都已完成因素映射。

已有一次查询批次覆盖候选发现、UTR 来源、默认来源、offer 和赔款+贸易组合；不需要为每个参数重复完整游戏流程。A/B 的一对真实执行覆盖了效果身份合同，C 验证了拒绝持久化，F/G 已分别验证接受后的原生效果和保存重载。后续新增来源或条款只有在角色、后果或存档合同发生变化时才需要新的对应业务分支。
