## 历史R50：贸易竞争力转移的查询、接受/拒绝与重载

`transfer_trade_power` 通过 `peace_context.terms` 传入统一议和接口。接口同时保留三种角色：`original_actor`/`original_recipient` 描述原提议方向，`decision_country` 描述作出回应的国家，条款中的 `source`/`beneficiary` 描述实际转出国和受益国。C 的一次显式 fixture 是 ENG→FRA 的 `demand` 提议，由 FRA 回应；实际条款仍是 `source=FRA`、`beneficiary=ENG`，因此不能把入站方向直接当成贸易转移方向，也不能把该 fixture 写成 NPC 自主发起。

A 的主动 offer 由 FRA 向 ENG 提供贸易转移，ENG 原生 AI 返回 `state=1/rejected`；B 的独立只读重载确认 FRA→ENG 精确关系和反向关系都不存在。C 将同一入站提议保存为 pending；D 从该保存得到 FRA 拒绝，战争继续且没有条约；E 得到 FRA 接受，战争结束并建立贸易转移。原生和公开效果读到比例 `500/1000`（50%）、`peace_treaty=true`、`start_date_raw=56545080`、`end_date_raw=43808760`。存档对应比例 `0.500`、强制标志 `is_enforced=yes` 和开始日期 `1454.12.2`，省略结束日期。F/G 分别从 D/E 的保存启动独立新进程，各9项检查通过，原生状态、存档精确/反向关系、战争状态和空 pending 队列相符。

保存块的字段为 `amount`、`is_enforced`、`first`、`second`、`start_date`，可以缺少 `end_date`；在已接受结果中 `first="FRA"` 映射为 source，`second="ENG"` 映射为 beneficiary。重载比较器将存档缺省的结束日期与原生哨兵 `43808760`（`0x29c77f8`）视为同一种“未指定固定终期”状态；有显式日期时仍比较日期。第三国贸易来源参数和接受因素标识继续补齐，随后扩展其他议和条款。

实际消费端修正均来自真实事件或原快照：原生已完成的组合曾被消费者写成格式错误；国家查找项缺少 `tag` 曾使只读探针失败；原生选中数为2（包含默认 Gold）曾被检查器按1判断；包装层 `parameters.complete` 的历史初值没有随真实 pending 绑定更新。C 的历史 `parameters.complete=false` 原样保留，但完整 `peace_context` 和真实绑定已单独核对。B 只对失败的只读探针重读一次，没有重放业务。

桥接还会读取和平提议实际传输的字段，逐项比较原提议与动作副本，并在原生规则查询后再次比较。R40的白和平和10金币提议都包含 **87个候选条款、19种实际类型**；双方、四组参与国、方向、各候选字段、定义名称及选中索引全部读取成功，副本与原提议相等，查询后保持不变。静态工厂表已覆盖40类条款；本场景实际出现的19类另有运行记录。

白和平的原生对象默认选中一个金额为0的金币条款，其余候选未选中；10金币查询将同一个条款改为10金币。公共接口把白和平的实际业务条款表示为 `terms:[]`，同时在 `native_payload` 中如实返回原生候选数量、选中数量和比较结果。候选中的对象地址和原始内部字段只保存在私有取证日志。

这批结果为后续议和授权提供了完整序列化字段的运行依据。下一步把这些字段接入授权、传输和执行入口，再完成实际议和与保存重载；`native_payload.authority_bound` 当前为 `false`。

## 当前已经可以查询什么

19项常用议和条款共用战争发现查询。查询返回当前双方关联的战争编号；同一场战争在不同条款、不同敌国和重复查询中使用同一编号。编号只在本次游戏观察会话内有效。AI 不需要接触游戏进程、对象地址或 DLL。

白和平的选中查询会让游戏构造一份没有加入具体条款的和平提议，再构造持有该提议副本的和平动作。查询分别调用动作合法性、通用外交条件和发送日期条件，读取诊断文本，最后调用游戏自身的析构函数释放临时对象。

R38B 的实际结果如下。这里的“通过”或“不通过”分别描述对应的原生条件。

| 法国的目标 | 提议本身合法性 | 通用外交条件 | 发送日期条件 | 游戏给出的具体原因 |
| --- | --- | --- | --- | --- |
| 英格兰 | 通过 | 不通过 | 通过 | 最近派遣过外交官，须等到1455年1月2日；当前没有可派遣外交官。 |
| 蒂罗尔 | 不通过 | 不通过 | 通过 | 附庸或被联合统治的国家不能签订和平条约；当前没有可派遣外交官。 |

接口将这两个目标的当前合法性返回为 `unavailable`，并保留原生中文说明。法国对英格兰的重复查询得到相同结果。英格兰对法国的查询按照现有信息范围规则返回范围不可用：当前接口只替法国查询，不因验收需要扩大可读取国家。

三个条件的结果分别保留。发送日期条件为真时，通用外交条件仍可能因为外交官不足或派遣冷却而失败；AI 应读取完整的合法性结果和原因。

## 英格兰当前怎样评价白和平

R38C 已在同一战争场景读取原生评价：总值为 **−45**，空条款提议的聚合分数为 **0**。两个分数来自不同原生函数，接口分别保存。

| 原生因素名称 | 稳定标识 | 原始数值 |
| --- | --- | ---: |
| 英格兰国内的起义 | `DIPLO_WAR_REBELS` | +1 |
| 英格兰控制着首都伦敦 | `DIPLO_HOLD_CAPITAL` | −5 |
| 战争持续时间 | `DIPLO_WAR_TIME_PASSED` | −45 |

| 盟友的相对实力 | `DIPLO_WAR_FORCE_BALANCE` | −1 |

这五项合计为−45，与本次原生总值一致。R39E 已把五项实际构造调用与原生本地化标识、数值、标志和最终文本逐项核对，完整输出上述标识。`acceptance.details_complete=true` 表示本次因素列表的标识、名称和原始数值已经全部取得。

`acceptance.native_total` 返回评价总值，`acceptance.items` 返回因素。`native_evaluation` 另保留本次是否调用评价、因素数量和数据核验状态；`costs.native_evaluation` 保存提议聚合分数。当前原始分数单位和响应阈值仍在核验，实际接受或拒绝由后续原生响应确认。

蒂罗尔的提议本身不合法，因此查询不调用其和平评价，总值返回 `null`。这个结果与英格兰的−45分分别保留。

## 指定金币数量会得到什么结果

AI可以明确指定索取金额，付款国为英格兰，收款国为法国。金额以金币为单位，精度为0.1金币。查询复用原生钱款上限和设额函数，再从原提议及动作副本分别回读金额。

| 请求金额 | 原提议与动作副本的实际金额 | 原生评价总值 | 提议聚合分数 | 参数结果 |
| ---: | ---: | ---: | ---: | --- |
| 10金币 | 均为10金币 | −100 | 1 | 匹配 |
| 20金币 | 均为20金币 | −100 | 1 | 匹配 |
| 865.1金币 | 保持空条款 | 未调用评价 | 未取得 | 超过当前865金币上限 |

当前场景仍有外交官及派遣冷却限制。金钱提议还返回三项额外接受因素：`DIPLO_WAR_INCONCLUSIVE`，原始值−1000，中文为“至少需要10点战争分数来提出要求”；`DIPLO_PEACEOFFER_VALUE`，原始值−1；`DIPLO_HIGH_DEMANDS`，原始值−2。加上白和平的五项，共8项，全部具有核验后的稳定标识、中文名称和数值。

该金钱提议的8项原始值合计−1048，原生评价总值为−100；接口分别保存游戏返回的总值和明细。`native_money`同时返回请求金额、当前上限、实际金额、付款国、收款国和副本核验结果。超限请求返回 `NATIVE_PEACE_MONEY_AMOUNT_EXCEEDS_LIMIT`，实际条款为空，供AI调整请求。

## AI 怎样调用

先发现法国与英格兰关联的战争：

```json
{
  "tool": "inspect_diplomatic_action",
  "action_id": "white_peace",
  "actor": "FRA",
  "recipient": "ENG",
  "phase": "initiate",
  "parameters": {}
}
```

从结果的 `war_contexts` 选择一个 `war_id`，再查询该战争的空条款提议。下例中的编号应替换成刚取得的实际编号。

```json
{
  "tool": "inspect_diplomatic_action",
  "action_id": "white_peace",
  "actor": "FRA",
  "recipient": "ENG",
  "phase": "initiate",
  "parameters": {
    "peace_context": {
      "war_id": "war_5673519a7126f7e2_00000001",
      "terms": []
    }
  }
}
```

游戏会重新读取双方战争关联，确认选中的战争仍存在。当前构造函数根据双方选择战争，因此双方同时关联多场战争时，接口会要求进一步区分，避免把查询套在另一场战争上。

结果中的 `native_validity`、`common_action_gate` 和 `initiation_gate` 对应上述三个判定；`diagnostics` 保存各判定的中文说明。`legality` 汇总当前状态及原因。`participant_copy_verified` 表示原提议与动作内提议的四组参与国序列一致；这项检查的范围是参与国复制。

查询指定金钱条款时，使用同一场战争编号，并明确金额及款项方向：

```json
{
  "tool": "inspect_diplomatic_action",
  "action_id": "demand_ducats",
  "actor": "FRA",
  "recipient": "ENG",
  "phase": "initiate",
  "parameters": {
    "peace_context": {
      "war_id": "war_5673519a7126f7e2_00000001",
      "direction": "demand",
      "terms": [{
        "action_id": "demand_ducats",
        "amount": "10.0",
        "payer": "ENG",
        "claimant": "FRA"
      }]
    }
  }
}
```

结果的`parameters.actual`列出实际写入临时提议的条款，`native_money.action_copy_verified`说明动作副本中的金额与原提议一致。本轮接口进行查询；后续执行会在完整战争与条款上下文中重新检查当前条件。
