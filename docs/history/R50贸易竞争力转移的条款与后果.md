# R50：贸易竞争力转移的条款与后果

本轮把议和条款“转移贸易竞争力”接入统一接口。实验玩家是葡萄牙（POR），桥接控制国是法国（FRA），英国（ENG）是另一方。A 中 FRA 向 ENG 主动提供贸易转移，ENG 原生 AI 明确拒绝；B 只读重载确认关系前后均不存在。C 是一次显式入站 fixture：原提议由 ENG 发给 FRA、由 FRA 回应，但条款实际转出国仍为 FRA、受益国为 ENG，不能把它解释为 NPC 自主发起。

D/E 从同一份 pending 保存分别得到 FRA 的拒绝和接受；拒绝保持战争且没有条约，接受结束战争并建立 FRA→ENG 的50%贸易转移。F/G 分别重载 D/E 的保存结果，原生条约、流式存档、战争状态和 pending 队列均匹配，各通过9项检查。A 至 G 使用同一65份源码的构建，最终[492项 Python 测试及264项子测试](../../work/runtime/r50-final-python-unit-20261018-001/report.json)通过。下文说明条款参数、原生证据、查询发现的问题、实际执行结果和重载核对；第三国贸易来源参数、缺失的接受因素标识和其他议和条款仍待扩展。

## 条款中两个国家分别表示什么

公开动作是 `transfer_trade_power`。条款的 `source` 表示转出贸易竞争力的国家，`beneficiary` 表示获得贸易竞争力的国家。法国向英国让步时，这两个国家分别是法国和英国；法国向英国索取时，默认要求英国向法国转移。完整和约继续记录战争编号、索取或让步方向，以及同时选中的其他条款。

这项和平条款转移50%的贸易竞争力，比例由游戏定义决定。接口不接受模型自行填写比例。当前本地游戏的 `PO_TRADE_POWER_AMOUNT=0.5` 与原有存档中的 `amount=0.500` 对应；原生整数为500，尺度为1000。公开结果还记录条约是否存在、强制转移标志和开始日期。

保存格式使用 `transfer_trade_power` 块，包含 `amount`、`is_enforced`、`first`、`second`、`start_date`，可以没有 `end_date`。本地化说明和平强制转移与停战期关联，因此验收没有套用战争赔款的十年期限。[定义与保存样例](../../work/runtime/peace-transfer-trade-native-20261017-r50-001/save-contract-evidence.json)保留了本地文件位置、哈希和有界样例。

## 原生如何选择和建立条约

贸易转移条款的原生类型是`0x2e07`，索引类别为8。它与战争赔款共用原生选择流程，但使用独立的虚表、描述符和重算函数。适配器在临时完整和约中选择条款，核对原提议、动作副本和查询后的完整载荷，再调用原生资格、互斥和费用检查。

[原生执行函数](../../work/runtime/peace-transfer-trade-native-20261017-r50-001/rea-9b6ae0/function.c)创建贸易转移条约，设置实际转出国、受益国、开始日期、比例和强制标志；[关系登记函数](../../work/runtime/peace-transfer-trade-native-20261017-r50-001/rea-a74860/function.c)和[转出方登记函数](../../work/runtime/peace-transfer-trade-native-20261017-r50-001/rea-a6a660/function.c)把条约加入国家关系。桥接只读取这些后果，条约由游戏自身执行函数创建。

## A：实际查询发现了什么

让步方向已经实际选中贸易转移条款，单项和金币、省份组合的原生合法性均通过。英国的接受因素明确给出“不希望转移贸易竞争力”，原生评价为−100；加入科克等五个省份后仍保留这项拒绝因素。[五省组合查询](../../work/runtime/diplomacy-query-20261017-r50-peace-a-trade-power/trade-power-query-001/money-five-provinces-trade-result.json)保存了八项接受因素及各自数值。

索取方向的原生候选列表只包含乌得勒支的贸易来源，没有英国自身的匹配条款。候选的原提议双方为英国和法国，实际转出国字段为乌得勒支。[原生候选构造函数](../../work/runtime/peace-transfer-trade-native-20261017-r50-001/rea-97eb70/function.c)分别生成本国来源和其他国家来源；本国来源受原生条件限制。这个场景要求接口继续区分提议双方与实际贸易来源，不能把任意候选直接当作英国自身。

`trade-power-query-002-correction.json` 对同一组原生事件做了离线公开投影修正，共五个 case，报告的解析、语义和公开检查全部通过。单项 `offer`、金币加四省、金币加五省以及 `mprt` 四类条款组合均为 `available`；四个可用结果的贸易转移候选都明确为 `source=FRA`、`beneficiary=ENG`，并且已选中。原生接受评分分别记录为−100、−100、−100、−100，组合聚合值为30、76、83、86；这些评分与“可构造、可提交的条款检查”是两个字段。

接受因素的中文文本和数值已经从原生结果导出。新增的 [R50 接受因素识别报告](../../work/runtime/r50-peace-factor-identification-20261018-001/report.json)显示，value6 的固定 `DIPLO_WAR_DESPERATION` 与备用动态文本取决于 `RBP+0x160` 是否非零；当前 capture 尚未读取这个条件，因此下一构建必须按实际文本分支补齐稳定标识。`mprt` 额外的−1000因素仍来自动态上下文，不能仅按 caller `0x1c120f` 固定映射。

索取 case 的请求方向是 `ENG→FRA`。修正后的公开状态为 `unknown`：候选数为1，但匹配数为0，`candidate_found=false`，原因是 `NATIVE_PEACE_TRADE_POWER_CANDIDATE_NOT_FOUND`，没有继续选中条款，也不再把它标成 `QUERY_NATIVE_RESULT_INVALID`。这保留了“没有英国自身来源候选”的事实，同时没有把不完整的规则信息误报成拒绝。该修正只复用了既有事件和输入输出，没有重新提交议和。[query002 修正报告](../../work/runtime/diplomacy-query-20261017-r50-peace-a-trade-power/trade-power-query-001/trade-power-query-002-correction.json)

首次查询还发现消费者错误：原生已完成金币、省份、赔款、贸易转移四类组合的选择和规则检查，Python却返回格式错误；本次未匹配到英国来源的查询也被归为格式错误。原始输入、公开输出和原生事件均保存在[查询目录](../../work/runtime/diplomacy-query-20261017-r50-peace-a-trade-power/trade-power-query-001)。消费者修正使用这些事件离线回放，原始报告继续保留。
