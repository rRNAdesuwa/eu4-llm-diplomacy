# 外来议和：查询提议、选择回应与保存结果

更新：2026-10-16。

法国已经通过统一接口分别拒绝和接受了英国的白和平提议。两次实验分别从同一份待回应存档启动：拒绝后提议移除、战争继续；接受后提议移除、战争结束。每次只提交一个业务请求，公开结果分别返回 `rejected` 和 `accepted`，各 20 项运行检查全部通过。

## AI 怎样查看与回应

游戏界面玩家为葡萄牙（POR），接口控制法国（FRA）。英国（ENG）仍使用游戏原生逻辑。外来议和统一使用动作 `peace_offer`，其中可以包含多个条款。

1. `list_diplomatic_actions` 的 `incoming_proposals` 返回提议编号、原提议国、接收国和动作类型。
2. 对 `peace_offer` 调用 `inspect_diplomatic_action`，阶段选择 `accept` 或 `reject`，参数传入公开的 `proposal_id`。这里的 `actor=ENG`、`recipient=FRA` 保留原提议方向，`decision_country=FRA` 表示法国作出回应。
3. 查询返回战争编号、原提议方向、已选条款、战争状态、原生规则结果与完整性字段。本次白和平的 `terms=[]`、`white_peace=true`；原生对象中的零金币条款已被识别为空提议。
4. `execute_diplomatic_action` 接收唯一请求编号和同一提议编号，执行前重新查询当前条件。`get_diplomatic_result` 读取同一请求的实际结果。

`peace_offer` 放在单独的入站动作定义中；原有 19 项议和条款继续表示构造和发送和约的具体条款。公开提议编号与战争编号属于当前观察器会话。内部原生编号、对象地址和传输字段由桥接保存，AI 无需提供。

## 实现如何连接原生执行

响应从保留的提议对象调用原生克隆函数，深复制完整和约，只修改接受或拒绝状态。原生克隆把两个日期字段都初始化为原提议日期，正常包装函数再写入当前发送日期。桥接保留原生提议编号、外交官字段、方向标志、参与国以及全部候选和已选条款。

回应随后经过原生最终包装规则、正常传输、完整载荷授权账本和通用命令执行入口。法国的议和处理器只接受已经消费该授权、且对象和完整条款匹配的回应。处理器实际返回后记录独立事件；结果接口再核对原生队列成员和双方战争状态。

已发送但尚未消费的回应保持提议预留状态。原生目标命令消费授权后才标记回应已提交。传输失败时归还桥接仍拥有的包装对象，并释放未消费的预留。

## 本轮检查发现的问题

- 旧账本要求所有议和的原生提议编号为 0；实际待处理提议编号为 199。现在发起仍要求 0，接受与拒绝保留原编号，后续各环节继续逐值比较。
- 首次真实查询返回完整合法结果，Python 却把布尔型 `native_current_war` 当成战争编号而拒收。已用真实 JSON 事件修复；战争编号从 `peace_context.war_id` 单独验证。
- 运行脚本最初读取了错误层级的规则完整性字段，第二次预检查因此停止。脚本改为读取公开 `native_inbound_inspection.response_rules_complete`。两次预检查均未执行外交回应；随后第三次运行只发送了一次业务请求。
- 接受议和会改变战争状态；验收脚本现按回应选择核对交战状态，不再沿用权限负例中“所有快照保持不变”的断言。

Python 全套 332 项通过；真实查询修复后定向 137 项通过；加入实际拒绝、接受事件后，Peace 定向 58 项通过。原生账本 384 项、入站 wire 与事件格式测试通过；A/B 构建均成功，A 仅编译，B 在独立新进程安装一次，C/D 复用同一不可变构建。[静态合同](../../work/runtime/peace-inbound-response-contract-20261016-r44-001/report.md)与[代码审阅](../../work/runtime/peace-inbound-response-contract-20261016-r44-001/review.md)保留了具体入口和检查发现。
