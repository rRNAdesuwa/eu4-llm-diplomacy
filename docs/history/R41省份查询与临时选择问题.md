## 先看结论

R41 已经能够通过统一的外交查询接口完成以下工作：

- 找到 FRA 与 ENG 共同参与的战争，并取得本次查询使用的 `war_id`。
- 查询原生省份候选列表。当前场景返回 41 条候选；每条候选包含省份 ID、中文名称和受益国。41 条记录的受益国全部是 `FRA`。
- 把一个省份（177）或两个省份（177、87）作为查询参数送入原生的省份条款对象，并回读候选、副本和原生临时结果。
- 用不存在的省份 ID `2147483647` 做负例。原生返回 `NATIVE_PEACE_PROVINCE_CANDIDATE_ABSENT`，没有把不存在的省份伪装成可选条款。

当前还不能把 `[177]` 或 `[177,87]` 说成已经写入一份可发送的和平提议。两次查询都产生了原生临时 delta，但回读的 `selected_province_ids` 都是空数组。后续需要找到真正的 UI 点击选择器，并接入有授权的执行路径；R41 只完成了查询和临时选择观察，没有提交和平请求。

## 统一外交接口的四个工具形状

项目的统一外交接口有四个工具。四个工具的职责不同，不能因为 `inspect_diplomatic_action` 返回了合法性或候选数据，就把查询当成提交。

| 工具 | 主要参数形状 | 作用 | R41 使用情况 |
| --- | --- | --- | --- |
| `list_diplomatic_actions` | `actor`、`recipient`、`category` | 列出动作目录和公开可见的入站提议 | 本轮操作器未调用；战争发现直接使用 `inspect` |
| `inspect_diplomatic_action` | `action_id`、`actor`、`recipient`、`phase`、`parameters` | 只读构造对象、读取原生规则、候选和副本 | R41 的全部实际查询都使用它 |
| `execute_diplomatic_action` | 唯一 `request_id` 加同一组动作参数 | 通过授权后提交一次业务动作 | R41 未调用，计数为 0 |
| `get_diplomatic_result` | `request_id` | 读取已经提交请求的终态和实际后果 | R41 没有提交请求，因此没有可读取的结果 |

R41 的“查询参数能回读”只说明 `inspect` 可以观察原生对象和临时结果。省份选择需要先由原生点击流程在提议对象中保留，再通过执行工具提交和约，并通过结果工具读取回应与后果。

## 本阶段的游戏边界

运行场景是暂停的游戏，葡萄牙（POR）是界面玩家，桥接替法国读取对英格兰的议和动作。R41C 使用的战争编号为 `war_8d2e3a29c3194f32_00000001`，动作方向为 `demand`，受益国为 `FRA`。查询开始和结束时的原生日期都是 `56545056`（1454 年 12 月 1 日），暂停标志和玩家槽位也没有变化。

本阶段所有调用都是只读查询。操作器记录了 `execute_call_count=0`、`time_advance_call_count=0` 和 `save_call_count=0`。外交官快照在查询前后相同，战争、联盟和控制状态的快照也相同。因此，R41 查询没有派出外交官、没有推进日期、没有保存游戏，也没有改变战争状态。

当前场景的原生合法性结果仍然显示两个实际游戏条件：

- 最近已经派遣过外交官，下一次派遣时间要等到 **1455 年 1 月 2 日**；
- 当前没有可供派遣的外交官。

这两个原因使 `common_action_gate=false`，所以 `legality.status` 为 `unavailable`。构造的整份和平动作返回 `native_validity=true`，而 `initiation_gate=true`；这说明“省份候选对象能够被构造和读取”与“此时能否向敌人发送和平协议”是不同条件。R41 只证明了查询不会消耗外交官，也没有证明将来的和平提交可以绕过外交官数量或派遣冷却。真正提交前仍须重新查询原生条件。

## 四种主要调用形状

操作器使用四种主要调用形状：战争发现、候选枚举、单省份选择和双省份选择。下面的 JSON 展示传给 `inspect_diplomatic_action` 的参数；每次调用仍然带有相应的 `action_id`、`actor`、`recipient` 和 `phase`。操作器另外增加一个不存在省份的负例，所以 R41C 实际完成了五次查询。

### 1. 发现战争

```json
{
  "action_id": "white_peace",
  "actor": "FRA",
  "recipient": "ENG",
  "phase": "initiate",
  "parameters": {}
}
```

返回结果用于取得共同战争的 `war_id`。这个调用只发现上下文，不发送白和平。

### 2. 枚举候选

```json
{
  "action_id": "cede_province",
  "actor": "FRA",
  "recipient": "ENG",
  "phase": "initiate",
  "parameters": {
    "peace_context": {
      "war_id": "war_...",
      "direction": "demand",
      "terms": []
    }
  }
}
```

空的 `terms` 表示“读取当前战争下的省份候选”，不是一份空的执行提议。

### 3. 请求一个省份

```json
{
  "peace_context": {
    "war_id": "war_...",
    "direction": "demand",
    "terms": [
      {
        "action_id": "cede_province",
        "province_ids": [177],
        "beneficiary": "FRA"
      }
    ]
  }
}
```

### 4. 请求多个省份

```json
{
  "peace_context": {
    "war_id": "war_...",
    "direction": "demand",
    "terms": [
      {
        "action_id": "cede_province",
        "province_ids": [177, 87],
        "beneficiary": "FRA"
      }
    ]
  }
}
```

操作器另外发送了一个负例：`province_ids=[2147483647]`。这个 ID 不在候选列表中，原生返回候选缺失原因。操作器还在本地拒绝了空的省份 ID 选择，因此没有把“空选择”误发成业务请求。

## B 阶段的 JSON 数组问题与修复

R41B 的原始 `native-events-slice.jsonl` 有一个传输格式问题：第 241 行和第 498 行的 `requested_province_ids`、`selected_province_ids` 数组各缺少一个结束方括号，共缺少四个 `]`。解析器因此无法直接读取两条事件，早期报告把字段标成缺失，不能据此判断原生没有候选。

修复过程保留了原始文件和原始 SHA-256，只在派生文件中补上四个数组结束符。派生回放得到两条事件，两个事件都通过原生观察器的结构和语义校验：候选数量为 41，候选列表包含 177；请求不存在的 `2147483647` 时，原生原因是 `NATIVE_PEACE_PROVINCE_CANDIDATE_ABSENT`。派生文件用于恢复字段级证据，不能被当作原始 DLL 已经发送出的字节流。

随后 native JSON helper 直接修正了数组输出。空数组、缺失候选和有选择候选三种 fixture 都能被标准 JSON 解析器读回。这个修复解决的是 JSON 序列化问题，不会把临时选择转换为持久选择。

## C 阶段：177 和 177+87 的真实结果

R41C 在同一暂停边界完成战争发现、候选枚举、单省份、双省份和缺失候选五次查询。原生事件的关键结果如下：

| 请求 | 找到请求候选 | 原生 toggle 次数 | `selection_delta_raw` | 回读 `selected_province_ids` | 副本核对 |
| --- | ---: | ---: | ---: | --- | --- |
| `terms=[]`（枚举） | 不适用 | 0 | 无 | `[]` | `true` |
| `[177]` | `true` | 1 | `8` | `[]` | `true` |
| `[177,87]` | `true` | 2 | `20` | `[]` | `true` |
| `[2147483647]` | `false` | 0 | 无 | `[]` | `true` |

单省份和双省份请求确实命中了候选，并且原生 toggle 返回了 8 和 20 的临时数值变化。两次请求的参数副本也都被正确读取；问题出在选择状态的生命周期：查询结束后，原生回读没有留下 177 或 87。

### 为什么有 delta 却没有选中省份

R41 的静态证据把省份条款的虚表 `+0x120` 定位到 `0x99d220`。这个函数接收完整的 `CPeaceOffer`，切换条款的选择字节，把条款放入临时向量，并返回一个有符号 delta。`0x99d220` 在返回前调用 `0x993520`；`0x993520` 遍历临时记录，把条款选择字节和相关向量恢复到调用前状态，再释放回滚记录。

因此，`8` 和 `20` 表示“原生临时计算曾经得到的数值变化”，不是“已经选中了 1 个或 2 个省份”。R41C 还记录到原生 payload 的 `selected_term_count=1`、`source_copy_equal=true`；这些字段证明和平对象已经被复制和检查，不能替代 `selected_province_ids` 的持久状态证明。

已找到的两个调用点也没有闭合持久选择：UI 列表路径 `0x130c410` 和发送侧回调 `0x130f080` 都进入 `+0x120`，但当前证据仍显示该路径经过 `0x993520` 回滚。真正的 selector 必须在长期存活的 `CPeaceOffer` 上留下条款选择字节、长期向量或序列化结果，并且调用结束后不立即进入这条回滚路径。

## 旧报告中 evaluation 检查为 false 的原因

R41C 原始报告中有三项 evaluation 检查显示 `false`。这三项不是“原生评价被调用”的证据，而是操作器当时从公共查询投影读取 `native_evaluation`；公共投影没有复制这个私有原生事件字段，所以消费者把“字段不存在”误判成了检查失败。

修正后的读取方式从同一批 `native-events-slice.jsonl` 中按 `query_id` 绑定 `native_peace_province_offer_inspection` 事件，再读取原生 `native_evaluation`。四条省份查询的原生 evaluation 都是 `called=false`、`score_available=false`、`aggregate_score_available=false`、`items=[]`。这是正确结果：候选枚举、缺失候选和未形成持久选择的请求没有进入评价阶段。操作器已经区分了两类问题：

- 公共消费者没有拿到私有 evaluation 字段，这是已修复的读取问题；
- 177 和 177+87 的 `parameters_matched=false`、`selected_province_ids=[]`，这是原生临时 toggle 回滚造成的真实选择问题。

## 下一步：真正的 selector 与 authority 执行

下一阶段需要完成两条独立链路：

1. 找到真实 UI 点击 selector。验证标准是同一个长期 `CPeaceOffer` 在点击前后，省份条款的选择字节、长期选择向量和序列化字段发生对应变化；不能只看 `0x99d220` 返回的 delta。
2. 在 selector 证明之后接入 authority 执行。执行前重新读取战争编号、FRA/ENG 双方、受益国、当前日期、外交官数量和派遣冷却；取得完整授权后只提交一次，再通过统一结果接口回读原生结果和和平状态变化。

当前接口可以给 AI 使用 41 条候选及其名称、受益国，也可以把指定省份作为查询参数并读取原生真实回读结果。当前接口还不能把查询参数直接当作已选和平条款，更不能据此发送和平协议。
