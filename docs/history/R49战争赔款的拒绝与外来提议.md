# R49：战争赔款的拒绝与外来提议

更新：2026-10-17。本轮完成两种场景：法国主动索取战争赔款时，英国原生AI明确拒绝；英国把包含战争赔款的和平提议送给法国后，法国从待处理队列读出完整条款，并分别执行拒绝和接受。接受后法国向英国支付十年赔款，英法战争结束；拒绝后没有赔款，战争继续。两种结果均已保存，并在独立新进程中核对战争、条约和待处理队列。

本文中的“战争赔款”对应原生动作 `war_reparations`。付款国是实际承担赔款的一方，收款国是获得赔款的一方。和平提议还会记录两个传输角色：`actor` 是原提议发起国，`recipient` 是收到待处理提议、拥有决策队列的国家；这两个角色不能直接当作付款国和收款国。`decision_country` 单独表示实际点击接受或拒绝的一方。

例如，法国主动向英国索取战争赔款时，原提议是 FRA → ENG，英国是付款国，法国是收款国。反过来，英国向法国送出 `direction="demand"` 的外来提议时，原提议是 ENG → FRA，法国是付款国，英国是收款国；法国负责回应，但不会因此变成原提议的发起国。

## C：从外来和平提议中读出完整战争赔款

C 从 R37 的战争存档开始，在 `1454.12.1` 构造了一次明确的 operator native fixture。它是测试程序主动调用原生接口生成的提议，不是游戏中 NPC 自发产生的外交行为。fixture 只 dispatch 一次：英国（ENG）向法国（FRA）发送 `direction="demand"` 的外来和平提议，要求法国支付战争赔款给英国。因此，原提议发起国是英国，接收待处理提议的国家是法国，付款国是法国，收款国是英国；法国后来作为 `decision_country` 负责回应。

原生待处理记录包含 83 个条款槽位，其中选中了 2 项：一个原生空金币项和战争赔款项。空金币项表示载荷中的空金币对象，不代表又发生了一笔真实付款。提议编号为 `1`，原生提议值和 token 都是 `199`，法国的待处理队列从 0 条增加到 1 条。C 的 fixture 报告还记录了 dispatch 被原生入口接受、完整载荷被放入法国队列，以及 `fra_decision_submitted=false`；这证明 C 只建立 pending 状态，没有替法国提交回应。

## 公共战争赔款语义与原生回应的连接

此前的缺口不在原生和平载荷：C、D、E 都能读到完整的 83 个条款槽位和 2 个选中项。缺口在公共上下文如何把原生条款解释成人能读取的角色。当前 `peace-inbound-context.inc` 识别战争赔款的原生 `type_id=0x30a0` 和 `bucket=7`，再检查条款的 `field10`、`field18`、`field22` 是否与提议的付款国和收款国一致，并核对 `direction` 与原始发起国、原始接收国。检查通过后，公共 `terms` 才输出 `war_reparations`、付款国和收款国。

回应绑定也按同一角色关系执行：桥接先从原始 pending 提议复制 `effect_request`，在调用原生回应处理器前读取战争和战争赔款的 `before` 状态；处理器返回后，再读取同一付款国、收款国和战争上下文的 `after` 状态。`decision_country=FRA` 只表示法国作出决定，不改变 ENG → FRA 的原始提议方向，也不改变法国付款、英国收款的条款角色。D 的拒绝结果验证了 `false → false`，E 的接受结果验证了 `false → true` 及实际日期，因此两种回应使用了同一条角色映射和状态比较路径。
