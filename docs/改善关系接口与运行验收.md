# 改善关系接口与运行验收

本文说明原生“改善关系”任务如何通过四个统一外交工具查询、提交和读取结果，并记录 R28 的实际运行证据。本文中的“改善关系”指派出一个外交官执行单方任务；它不是需要目标国家接受或拒绝的外交提议。

## 当前角色和控制边界

本轮实验中的国家角色如下：

| 国家 | 角色 | 作用 |
|---|---|---|
| POR，葡萄牙 | 玩家国家 | 游戏由 POR 玩家控制。查询和执行前，运行层确认玩家国家为 POR，游戏处于暂停状态。 |
| FRA，法国 | 接口行动国 | API 以 FRA 为 `actor` 发起任务。原生执行权限只覆盖 FRA 的任务，接口不会把 POR、PRO 或 SAV 冒充成行动国。 |
| PRO，普罗旺斯 | NPC 目标国 | 可作为查询目标；本轮改善关系的实际提交目标不是 PRO。 |
| SAV，萨伏依 | NPC 目标国 | R28b 实际提交的目标。SAV 不需要作出接受或拒绝决定，游戏只记录 FRA 的外交官任务。 |

POR 的玩家控制和 FRA 的接口行动国是两种不同关系：POR 决定当前游戏会话和暂停状态，FRA 才是本接口提交原生外交任务的行动方。PRO、SAV 等目标国家仍由游戏规则和 NPC 逻辑处理。

## 动作合同

两个动作都使用 `native_identifier = "improve_relations"`，阶段固定为 `initiate`，参数固定为空对象 `{}`：

| `action_id` | 中文含义 | 接受度 | 目标条件 |
|---|---|---|---|
| `improve_relations` | 改善关系 | `not_applicable` | FRA 对一个可解析的三字母国家标签发起。 |
| `stop_improving_relations` | 停止改善关系 | `not_applicable` | FRA 停止自己已经登记的任务。 |

游戏引擎按原生流程选择外交官，调用方无需提供 `diplomat_id`。接口在提交前重新读取当前外交官任务、外交官可用数、原生按钮可见性和合法性；查询结果中的 `acceptance` 始终明确返回 `not_applicable`，不会生成接受度分数或接受/拒绝预测。

当前执行适配要求安装包提供专用的 `native_improve_relations_submission` 能力确认。查询能力由独立的 `native_improve_relations_query` 确认。查询结果显示“可用”只说明游戏当前允许发起，不能替代执行能力确认。

## 四个统一工具的调用方法

`tools/diplomacy.py` 使用 JSON Lines。每行包含 `tool` 和 `arguments` 两个字段。下面的例子以 FRA 查询和操作 SAV 为例；工具返回的 `session`、`legality`、`authorization` 和 `result` 字段应按当前运行结果读取。

### 1. 列出动作

```json
{"tool":"list_diplomatic_actions","arguments":{"actor":"FRA","recipient":"SAV","category":"diplomatic_action"}}
```

`list_diplomatic_actions` 返回动作目录、参数定义以及当前会话对查询和执行的支持状态。改善关系动作的参数定义为空，执行支持只有在当前安装确认了原生提交能力时才会显示。

### 2. 查询当前合法性和原生诊断

```json
{"tool":"inspect_diplomatic_action","arguments":{"action_id":"improve_relations","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
```

停止任务使用相同结构，只需把 `action_id` 换成 `stop_improving_relations`。查询结果的关键字段含义如下：

- `legality.status` 表示当前原生规则是否允许该动作。
- `native_diagnostic.text` 是游戏当前返回的可读诊断文本。
- `resources.diplomats.available_count` 表示当前可用外交官数量。
- `native_rule_components` 记录外交列表可见性、按钮条件和具体合法性检查是否通过。
- `acceptance.applicability` 对这两个单方任务为 `not_applicable`。

### 3. 提交一次任务

```json
{"tool":"execute_diplomatic_action","arguments":{"request_id":"r28b_improve_sav_001","action_id":"improve_relations","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
```

`request_id` 必须由调用方为本次业务请求提供唯一值。执行工具会在提交前重新执行健康检查和原生合法性检查，再决定是否向游戏投递。返回 `submitted=true` 只表示请求已经取得原生提交回执；接口还要等待并核对后续结果，才能把业务状态标记为 `executed`。

停止任务的调用形式如下：

```json
{"tool":"execute_diplomatic_action","arguments":{"request_id":"r28c_stop_improve_sav_001","action_id":"stop_improving_relations","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
```

同一个 `request_id` 不能绑定另一组动作或参数。重复调用会读取已有记录并返回同一业务结果，不能再次向游戏提交。

### 4. 读取结果

```json
{"tool":"get_diplomatic_result","arguments":{"request_id":"r28b_improve_sav_001"}}
```

结果读取会把请求、会话、动作、双方国家、阶段和游戏日期与原生事件逐项对应。改善关系的成功结果包含 `family="improve_relations"`、`native_state=0`、动作对应的 `native_variant`、`task_before`、`task_after`、`execution_verified=true` 和 `request_binding_verified=true`。缺少完整原生事件时，接口保持 `unknown` 或 `submitted`，不会把排队回执当成任务已经执行。

## R28a 查询验收

R28a 在 POR 玩家暂停的会话中查询了 FRA 对 ENG、PRO、SAV 的 `improve_relations` 和 `stop_improving_relations`，共六个查询。查询报告为[改善关系查询报告](../work/runtime/diplomacy-query-20261015-r28-improve-a/improve-relations-queries-095be3fff8b3422e9a20335ec86ed65c/report.json)。

没有现有任务时，三个目标的 `improve_relations` 都满足以下条件：

- 原生外交列表可见，按钮选择和具体合法性检查通过，`legality.status=available`。
- 原生诊断为“改善你与这个国家的关系。”。
- 可用外交官数量为 1，且原生规则确认该资源可用于发起。
- `acceptance.applicability=not_applicable`。

同一基线下，三个目标的 `stop_improving_relations` 都不可用。动作隐藏，原生规则返回了具体目标的“未与……改善关系”诊断；例如 SAV 的文本为“§R- 未与萨伏依改善关系。§!”。这说明停止动作的合法性依赖当前是否存在 FRA 对该目标的任务。

R28a 是查询层实验，因此其目录输出中的执行状态仍是观察模块状态。实际执行能力由后续 R28b 安装单独确认；使用者应以当前 `list` 和 `inspect` 返回的 `authorization` 与 `interface_support.execute` 为准。

## R28b 实际开始任务

R28b 使用请求 `r28b_improve_sav_001`，由 FRA 向 SAV 发起 `improve_relations`。执行报告为[改善关系执行报告](../work/runtime/diplomacy-query-20261015-r28-improve-b/improve-relations-execution-a960cdb03c8b4405a4ba275dadad4580/report.json)。本次实际操作和结果如下：

1. 提交前，FRA 没有这条 SAV 任务，原生任务选择器为 `11739`，FRA 可用外交官数量为 1。
2. 接口只调用了一次执行入口，原生提交回执和后续结果事件均与同一个 request、session、动作、双方国家和日期相符。
3. 原生结果事件的 `family` 为 `improve_relations`，`native_state=0`、`native_variant=1`，`task_before=false`、`task_after=true`，两个验证字段均为 `true`。
4. API 最终返回 `submitted=true`、`status=executed`、`game_outcome=executed`。这表示 FRA 的外交官任务已经在游戏中登记。
5. 执行后，FRA 可用外交官数量由 1 变为 0，任务表中出现一个活动的 11739 任务。SAV 没有接受或拒绝步骤。

相同请求编号的重复读取返回了相同的 `executed` 结果，journal 重新打开后仍返回相同的公开结果；执行入口调用次数保持为 1。这两项分别验证了 API 幂等性和结果记录的重开稳定性。

## 保存、重载和持续任务

开始任务后的活动存档为 `llm_diplomacy_improve_sav_active_20261015_r28b.eu4`，SHA-256 为 `c99737d693cda74106bba56cfa0c89977b6e152f81f890bc94fa062e0ba44ad4`。

新进程载入该存档后，运行层再次确认 POR 玩家、暂停状态、当前日期和 FRA 的活动 11739 任务；外交官数量仍为 0。对应的[活动存档重载报告](../work/runtime/diplomacy-query-20261015-r28-improve-c-active-reload/improve-relations-reload-25ca854b6dc844088c3a9562621ca2d8/report.json)通过了新进程身份、存档哈希、任务身份和四类快照检查。

随后游戏自然推进 35 天至 1445.4.16。只读验证仍发现 FRA 的 11739 任务处于活动状态，说明任务跨日期持续存在；[35 天后的只读验证报告](../work/runtime/diplomacy-query-20261015-r28-improve-c-active-reload/improve-relations-reload-4220c84b467c4045bb0b3909935070a3/report.json)通过。对应的持续状态存档为 `llm_diplomacy_improve_sav_35days_20261015_r28c.eu4`，SHA-256 为 `ae5b1b8398ede8809feb04614c280c87b49c8b25885bd95a91718fd6ab11f163`；[存档观察报告](../work/runtime/diplomacy-query-20261015-r28-improve-c-active-reload/save-observer-report-1792050504712206200.json)记录了该文件的玩家和日期。

[三份存档对照](../work/runtime/r28-improve-save-effects-20261015-001/report.md)进一步读出了 `improved_relation` 对应的 `opinion.current_opinion`：法国对萨伏依为 `3.500 → 7.000`，萨伏依对法国为 `7.000 → 14.000`。停止任务的同日存档保留了后两个值。这些数值是关系修正项的原始存档值；显示界面的总关系值需要另行包含其他修正。

## 停止任务和当前状态

停止任务使用 `r28c_stop_improve_sav_001`。第一次[停止执行报告](../work/runtime/diplomacy-query-20261015-r28-improve-c-active-reload/improve-relations-execution-fc65045f9e0c4f2896080eb2e778ff51/report.json)保留为 failed，因为旧校验器把停止后的 `active_raw_18=1` 误判为仍在工作；原生事件本身已经报告 `executed`、`task_before=true`、`task_after=false`、`native_state=0`、`native_variant=0`。随后沿用同一 request 读取并运行修正后的验证，未重新提交，获得了[停止任务修正验证报告](../work/runtime/diplomacy-query-20261015-r28-improve-c-active-reload/improve-relations-resume-140842721add4c728f9591084f99b639/report.json)。

## 执行入口 guard 的独立取证

统一执行入口必须同时覆盖直接调用和虚表调用。独立 Windows fixture 实际运行了四条路径：

- direct CALL 放行：guard 调用一次，原始函数体执行一次，返回值正确，RBX/RBP/RSI/RDI/R14 保持不变。
- virtual-table CALL 放行：guard 调用一次，原始函数体执行一次，返回值正确，非易失寄存器保持不变。
- direct CALL 拦截：guard 调用一次，原始函数体执行零次，返回拦截哨兵值。
- virtual-table CALL 拦截：guard 调用一次，原始函数体执行零次，返回拦截哨兵值。

fixture 还验证了 trampoline、入口跳转和 Windows unwind 注册。完整结果见[通用执行入口 fixture 报告](../work/runtime/fixture-generic-execution-entry-20261015-001/report.md)和[fixture 结构化验证](../work/runtime/fixture-generic-execution-entry-20261015-001/verification.json)。

原生 PE 取证报告对目标入口只做有界读取：入口 18 字节序言与 fixture 相同；原生 `.pdata` 关联的 unwind 语义包含 32 字节栈分配、R14/RDI/RSI 压栈以及 RBP/RBX 保存，与 fixture 的栈帧语义一致。生产代码为 trampoline 注册目标函数原有的 `parent.UnwindData`，保留原生异常清理标志；独立 fixture 使用手工编码验证相同的栈帧语义。[原生 PE 取证报告](../work/runtime/fixture-generic-execution-entry-20261015-001/native-pe-evidence-20261015-001/report.md)和[结构化 PE 证据](../work/runtime/fixture-generic-execution-entry-20261015-001/native-pe-evidence-20261015-001/evidence.json)保存了完整来源。

## 游戏内授权与拦截验证

R28e2 在同一个暂停会话中先后调用两个合法的原生改善关系测试包。测试包没有桥接授权，分别通过[原生函数直接入口](../work/runtime/diplomacy-query-20261015-r28-improve-e2-authority/authority-test-ce144ee555704f3e8727d1f34ca804f1/report.json)和[正常投递入口](../work/runtime/diplomacy-query-20261015-r28-improve-e2-authority/authority-test-9cd6bb988a68492293afcecedd08930f/report.json)进入执行检查。两轮均得到 `UNAUTHORIZED_FRA_IMPROVE_TASK`，法国、英国和葡萄牙的外交官任务与可用数保持不变。随后同一版本的[授权开始请求](../work/runtime/diplomacy-query-20261015-r28-improve-e2-authority/improve-relations-execution-816e4c64974944068d80202b470bc696/report.json)成功建立 FRA→SAV 任务，返回 `executed`。

[独立来源对照](../work/runtime/diplomacy-query-20261015-r28-improve-e2-authority/improve-relations-authority-source-comparison-ddf20b2a5ad046d8b0d35d8c25cfb481/report.md)通过51项检查，分别关联直接入口和投递入口的真实对象、执行拒绝和外交官快照。这两轮拦截使用人为构造的合法原生包，核对的是实际入口的授权行为。原生 AI 直接调用相同执行函数的来源已在静态分析中定位；本轮自然推进期间没有记录到它自发提出新的 FRA 改善关系任务。
