# 军事通行权接口与运行验收

本文说明当前统一外交接口中的军事通行权（Military Access）动作。本文面向两类读者：需要调用外交接口的 AI，以及需要根据运行报告判断接口行为的人类开发者。

R32 已完成法国对勃艮第的拒绝、法国对萨伏依的接受、活动关系新进程重载、正反方向查询、萨伏依入站请求拒绝、萨伏依通行权取消，以及热那亚自然提议由法国接受。GEN 测试提议的跨日保持和 D 轮四方向重载分别按实际结果记录；本文中的“已通过”只对应列出的实际报告。

## 1. 国家角色和关系方向

本实验使用 POR（葡萄牙）作为游戏内玩家国家，使用 FRA（法兰西）作为 LLM 实际控制的外交行动国。POR 负责提供玩家、暂停、日期和存档会话；POR 不是下列军事通行权动作的 `actor`。SAV 是萨伏依，BUR 是勃艮第，LIT 是立陶宛，GEN 是热那亚。除 FRA 外，这些国家继续由游戏原生规则和原生 AI 控制。

军事通行权是单向关系。接口中的箭头表示“请求通行的一方 → 授予通行的一方”，而不是“授予方 → 请求方”：

| 业务场景 | `actor` | `recipient` | 关系含义 | 决策者 |
| --- | --- | --- | --- | --- |
| 法国请求进入萨伏依领土 | `FRA` | `SAV` | FRA 在 SAV 通行；查询结果是 FRA→SAV | SAV 的原生 AI |
| 法国请求进入勃艮第领土 | `FRA` | `BUR` | FRA 在 BUR 通行；查询结果是 FRA→BUR | BUR 的原生 AI |
| 萨伏依请求进入法国领土 | `SAV` | `FRA` | SAV 在 FRA 通行；查询结果是 SAV→FRA | FRA 的 LLM |
| 热那亚请求进入法国领土 | `GEN` | `FRA` | GEN 在 FRA 通行；查询结果是 GEN→FRA | FRA 的 LLM |

出站请求使用 `actor=FRA`。入站请求保留提出请求的 NPC 作为 `actor`，使用 `recipient=FRA`；FRA 对入站请求使用 `phase=accept` 或 `phase=reject` 作出选择。入站响应不能把双方交换成 `actor=FRA, recipient=SAV`，否则查询的是另一条方向相反的关系。

R32B 的实际反向查询给出了这个区别：同一日期下 FRA→SAV 为 `military_access_active=true`，SAV→FRA 为 `false`。萨伏依随后向 FRA 发出的请求被 FRA 拒绝，FRA→SAV 的既有通行权仍然保持活动。

## 2. 统一外交 API 合同

四个统一接口的职责如下：

| API | 用途 | 关键输入 | 关键输出 |
| --- | --- | --- | --- |
| `list_diplomatic_actions` | 列出动作目录和 FRA 的入站提议 | `actor`、`recipient`、`category`；查询入站提议时使用 `recipient="FRA"` | 动作目录、支持状态、`incoming_proposals` 和公开 `proposal_id` |
| `inspect_diplomatic_action` | 只读查询当前可见性、合法性、接受因素和关系 | `action_id`、`actor`、`recipient`、`phase`、`parameters` | `visibility`、`legality`、`acceptance`、`relationship_state`、资源和原生诊断 |
| `execute_diplomatic_action` | 按最新查询结果提交一个动作或一个入站响应 | 唯一 `request_id` 加动作参数 | `submitted`、原生收据、结果关联 |
| `get_diplomatic_result` | 读取已提交请求的终态 | `request_id` | `accepted`、`rejected` 或 `executed`，以及关系前后值 |

### 2.1 出站请求和单方取消

`ask_military_access` 和 `cancel_military_access` 都使用 `family="military_access"`、`phase="initiate"` 和空参数对象 `{}`。出站请求的调用顺序如下：

```json
{"tool":"list_diplomatic_actions","arguments":{"actor":"FRA","recipient":"SAV","category":"diplomatic_action"}}
{"tool":"inspect_diplomatic_action","arguments":{"action_id":"ask_military_access","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
{"tool":"execute_diplomatic_action","arguments":{"request_id":"r32_access_sav_001","action_id":"ask_military_access","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
{"tool":"get_diplomatic_result","arguments":{"request_id":"r32_access_sav_001"}}
```

`ask_military_access` 的实际终态可能是 `accepted` 或 `rejected`。接受时关系从 `military_access_before=false` 变成 `military_access_after=true`；拒绝时关系保持 `false`。关系前后值必须以原生结果和公开 `relationship_state` 为准。

已经存在 FRA→SAV 通行权时，取消动作使用同一方向：

```json
{"tool":"inspect_diplomatic_action","arguments":{"action_id":"cancel_military_access","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
{"tool":"execute_diplomatic_action","arguments":{"request_id":"r32_cancel_sav_001","action_id":"cancel_military_access","actor":"FRA","recipient":"SAV","phase":"initiate","parameters":{}}}
{"tool":"get_diplomatic_result","arguments":{"request_id":"r32_cancel_sav_001"}}
```

取消是单方关系操作，预期终态为 `executed`。取消成功时 `military_access_before=true`、`military_access_after=false`。外交官返程、冷却期或没有可用外交官时，取消的 `legality.status` 可能为 `unavailable`；关系是否仍存在必须单独读取，不能用外交官任务状态代替关系状态。

### 2.2 FRA 响应入站提议

调用方先从 `list_diplomatic_actions` 返回的 `incoming_proposals` 复制公开 `proposal_id`。公开编号是当前会话中的不透明标识；调用方不提交原生内存中的 proposal 数字 ID。

例如，萨伏依向法国请求通行权时，调用顺序如下：

```json
{"tool":"list_diplomatic_actions","arguments":{"recipient":"FRA","category":"diplomatic_action"}}
{"tool":"inspect_diplomatic_action","arguments":{"action_id":"ask_military_access","actor":"SAV","recipient":"FRA","phase":"reject","parameters":{"proposal_id":"从 incoming_proposals 复制的公开编号"}}}
{"tool":"execute_diplomatic_action","arguments":{"request_id":"r32_reject_sav_access_001","action_id":"ask_military_access","actor":"SAV","recipient":"FRA","phase":"reject","parameters":{"proposal_id":"从 incoming_proposals 复制的公开编号"}}}
{"tool":"get_diplomatic_result","arguments":{"request_id":"r32_reject_sav_access_001"}}
```

接受时把 `phase` 改为 `accept`，并保留同一个 `proposal_id`：

```json
{"tool":"inspect_diplomatic_action","arguments":{"action_id":"ask_military_access","actor":"GEN","recipient":"FRA","phase":"accept","parameters":{"proposal_id":"从 incoming_proposals 复制的公开编号"}}}
{"tool":"execute_diplomatic_action","arguments":{"request_id":"r32_accept_gen_access_001","action_id":"ask_military_access","actor":"GEN","recipient":"FRA","phase":"accept","parameters":{"proposal_id":"从 incoming_proposals 复制的公开编号"}}}
```

入站响应的接受度 `applicability` 为 `not_applicable`，因为 FRA 正在作决定。最终结果由原生响应事件确认，而不是由某个接受度预测字段代替。入站接受时，关系是 `GEN→FRA`；查询取消或关系状态时也必须使用 `actor=GEN, recipient=FRA`。

## 3. 两个动作的结果字段

### 3.1 出站 `ask_military_access`

| 字段 | 接受 | 拒绝 |
| --- | --- | --- |
| `game_outcome` / `status` | `accepted` | `rejected` |
| `event` | `native_diplomacy_relation_response_result` | `native_diplomacy_relation_response_result` |
| `native_state` | `2` | `1` |
| `native_variant` | `1` | `1` |
| `military_access_before` → `after` | `false` → `true` | `false` → `false` |
| `response_verified` | `true` | `true` |
| `request_binding_verified` | `true` | `true` |

### 3.2 单方 `cancel_military_access`

| 字段 | 预期值 |
| --- | --- |
| `game_outcome` / `status` | `executed` |
| `event` | `native_diplomacy_relation_execution_result` |
| `native_state` | `0` |
| `native_variant` | `0` |
| `military_access_before` → `after` | `true` → `false` |
| `execution_verified` | `true` |
| `request_binding_verified` | `true` |

入站 `ask_military_access` 仍使用 `native_variant=1`、`native_state=2`（接受）或 `1`（拒绝），并且响应事件必须匹配原始 `actor`、`recipient=FRA`、阶段和公开 proposal。入站响应成功消费提议时，原生结果中的 `pending_removed=true` 是提议消费证据。

### 3.3 查询中的合法性、接受度和关系

`inspect_diplomatic_action` 返回的 `legality.status` 是当前原生按钮和执行规则的结果，可取 `available` 或 `unavailable`；`visibility.status` 表示动作是否在当前外交列表可见。两个字段描述“现在能不能发起”，不描述目标国之后一定会接受。

对于出站 `ask_military_access`，`acceptance` 当前导出：

- `native_total`：原生有符号整数；
- `native_threshold`：当前实测为 `1`；
- `native_would_accept` 和 `predicted_response`：当前原生接受检查的预测；
- `items`：每一条原生原因文本和 `native_value`；
- `costs`：当前报告状态为 `unknown`，没有编造费用或单位。

对于 `cancel_military_access` 和入站 `accept`/`reject`，接受度是 `not_applicable`。AI 应使用 `relationship_state.military_access_active` 读取业务关系，并检查 `relationship_state.complete`；`military_access_state_verified` 可作为原生状态核验字段。外交官任务数组中的 `active_raw_18` 只描述外交官任务，例如派出、工作或返程，不能代替军事通行权关系。

## 4. 四个运行工具

下面四个脚本对应统一接口的查询、执行、重载和入站响应流程。命令中的 `installation.json` 应替换为当前新进程的安装记录；日期使用与该安装绑定的 `date_raw`，不要跨实验复用旧日期。

### 4.1 只读查询：[`run_military_access_queries.py`](../work/run_military_access_queries.py)

该工具对每个 `--recipient` 查询 `ask_military_access` 和 `cancel_military_access`，输出合法性、可见性、接受因素、外交官资源和 `relationship_state`。工具不会发布执行请求。

```powershell
python work/run_military_access_queries.py --installation work/runtime/diplomacy-query-20261015-r32-military-access-a/installation.json --expected-date-raw 56463768 --recipient SAV --recipient BUR --expected-legality SAV=available --expected-military-access SAV=absent
```

`--recipient` 可以重复使用。未提供 `--expected-legality` 或 `--expected-military-access` 时，工具仍会记录原生返回值，但不把未指定的期望当成失败条件。

### 4.2 一次执行或只读恢复：[`run_military_access_execution.py`](../work/run_military_access_execution.py)

执行工具对 `ask_military_access` 接受／拒绝和 `cancel_military_access` 执行使用不同的终态合同。执行工具默认使用 raw date `56463768`；跨日期或重载场景应显式传入当前安装报告中的 `--expected-date-raw`：

```powershell
python work/run_military_access_execution.py --installation work/runtime/diplomacy-query-20261015-r32-military-access-a/installation.json --action-id ask_military_access --recipient SAV --request-id r32_access_sav_001 --expected-outcome accepted --expected-date-raw 56463888
python work/run_military_access_execution.py --installation work/runtime/diplomacy-query-20261015-r32-military-access-c-revoked-reload/installation.json --action-id cancel_military_access --recipient SAV --request-id r32_cancel_sav_001 --expected-outcome executed --expected-date-raw 56463912
```

工具在一次提交后进行有界结果轮询，记录四类快照、原生日志切片、结果幂等读取和 SQLite 重开读取。相同 `request_id` 的重复调用只读取已有结果，不重新投递。原执行报告出现超时或消费端读取错误时，应把原报告目录传给 `--resume-artifact` 进行只读恢复；不要用新请求号重放原生动作：

```powershell
python work/run_military_access_execution.py --installation work/runtime/diplomacy-query-20261015-r32-military-access-b-active-reload/installation.json --resume-artifact work/runtime/diplomacy-query-20261015-r32-military-access-b-active-reload/military-access-execution-EXAMPLE --expected-date-raw 56463912
```

### 4.3 新进程重载：[`validate_military_access_reload.py`](../work/validate_military_access_reload.py)

重载工具只读验证新进程是否从存档恢复了指定方向的关系。`--expected-military-access active` 验证关系存在，`absent` 验证关系不存在；重载工具不会发布取消或请求。

```powershell
python work/validate_military_access_reload.py --installation work/runtime/diplomacy-query-20261015-r32-military-access-b-active-reload/installation.json --expected-date-raw 56463888 --recipient SAV --expected-military-access active --save-path "C:\Users\wangyufei\Documents\Paradox Interactive\Europa Universalis IV\save games\llm_diplomacy_access_sav_active_bur_rejected_20261015_r32a.eu4" --reference-artifact work/runtime/diplomacy-query-20261015-r32-military-access-a/military-access-execution-4391ee4ac87a4d47bf1d4037609c5dde
```

重载验收必须同时核对 POR 玩家身份、暂停标记、日期、四份快照、源构建和 DLL 绑定。关系验收使用原始方向；入站 SAV→FRA 的结果不能用 FRA→SAV 的方向替代。

需要在同一新进程一次核对多个方向时，使用只读组合工具 [`validate_military_access_directions_reload.py`](../work/validate_military_access_directions_reload.py)。工具默认核对 `FRA→SAV=absent`、`SAV→FRA=absent`、`CAS→FRA=active` 和 `FRA→CAS=absent`，也可以用重复的 `--direction ACTOR->RECIPIENT=active|absent` 指定方向集合：

```powershell

```

该组合工具每个方向都查询 `ask_military_access` 和 `cancel_military_access`，保留 `actor`、`recipient`、`phase`、合法性、可见性和 `relationship_state`。工具只发原生查询，不调用 `execute_diplomatic_action`，不把外交官返程状态当作通行权关系。

### 4.4 FRA 响应入站提议：[`run_alliance_inbound_response.py`](../work/run_alliance_inbound_response.py)

该脚本的旧 Alliance、Royal Marriage 和 Support Independence 分支保持兼容，军事通行权使用 `--action-id ask_military_access`：

```powershell
python work/run_alliance_inbound_response.py --installation work/runtime/diplomacy-query-20261015-r32-military-access-b-active-reload/installation.json --action-id ask_military_access --actor SAV --decision reject --request-id r32b_reject_sav_access_001
```

脚本会列出 FRA 的入站提议，复制匹配的公开 proposal，按 `actor=SAV, recipient=FRA` 查询和提交响应，然后读取原生响应事件和关系后果。`--actor` 可换成其他三字母 NPC，例如 `GEN`。

在受控 native fixture 中生成测试提议时可以追加 `--generate-test-proposal`。该选项写入 `TEST_ONLY MILITARY_ACCESS_TO_FRA <ACTOR>\n` 类型的私有测试命令，用于建立可观察的原生提议来源；该选项不代表自然外交 AI 已经自主发起，也不由脚本控制游戏推进。

## 6. 实际运行验收

## 7. 调用方的最小决策流程

AI 在每次外交操作中应按照下列顺序工作：

1. 确定业务方向。法国向目标国请求时使用 `FRA→目标国`；目标国向法国请求时保留 `目标国→FRA`。
2. 用 `inspect_diplomatic_action` 读取同一方向、同一动作的 `visibility`、`legality` 和 `relationship_state`。
3. 对出站 `ask_military_access` 读取 `acceptance.native_total`、原因行和 `native_would_accept`；把预测作为决策输入，不把预测当作已经发生的接受。
4. 对入站请求从 `incoming_proposals` 复制 `proposal_id`，用 `phase=accept` 或 `phase=reject` 查询后提交同一个 proposal。
5. 使用新的唯一 `request_id` 提交一次；随后用 `get_diplomatic_result` 等待 `accepted`、`rejected` 或 `executed`。
6. 以结果事件中的 `military_access_before/after`、原生状态、variant、request binding 和 `relationship_state.military_access_active` 共同确认业务后果。
7. 需要持久性时，在同一方向执行新进程重载查询。不要用外交官是否空闲推断通行权是否存在。

## 8. 当前字段边界

接口已经可以导出军事通行权的动作目录、原生可见性、合法性、接受因素原生值、预测接受结果、单向关系状态、出站实际响应、入站 proposal 响应和保存重载结果。以下字段目前保留原生返回并明确标记状态：

| 字段 | 当前状态 |
| --- | --- |
| raw date 编码与日历换算 | `date_raw` 已绑定并用于同实验比较，编码换算规则尚未作为公开合同固定 |
| 费用、金币、外交点或单位消耗 | 当前查询 `costs.status="unknown"`，没有可验证成本数据 |
| 接受因素单位和尺度 | `native_value` 为 signed int32；百分比、外交点或其他单位尚未确认 |
| 原因文本编码完整性 | 文本已解码并返回，但 `text_encoding_verified` 仍按记录保留；不能把本地化文本当稳定 ID |
| subject／overlord 条件原因 ID | E 轮通过原生文本 flag 和分支字节确定；标准分支与宗主分支均已实际命中并分别导出稳定 ID |

这些字段边界不会影响已验证的状态机和关系结果：关系是否存在由公开 `relationship_state` 与对应 native result event 共同确认；动作是否当前可投递由原生 `legality.status` 确认；出站请求最终被接受还是拒绝由实际 `native_diplomacy_relation_response_result` 确认。
