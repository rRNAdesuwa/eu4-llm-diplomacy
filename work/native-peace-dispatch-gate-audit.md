# Native peace dispatch gate audit

审计范围：`eu4.exe` 的 `RVA 0x4e7c80`（文件 `work/runtime/peace-repeat-4e7c80.txt`），并对照 `+0x80` 方法 `RVA 0x59b480` 与预览方法 `RVA 0x59bf10`。本轮只读离线反汇编；没有注入、发送动作或修改游戏/DLL代码。

## `country+0x24a0` 的明确写入门槛

写入位于 `0x4e8111`：

```text
country = country_table[(action+0x10 >> 32) sign-extended]
country->0x24a0 = global_date->0x1dd0
```

到达该写入点的可确认条件，按执行顺序是：

1. `0x4e7ca1` 调用 action vtable `+0x80`，返回 `AL != 0`。若 `AL == 0`，跳到 `0x4e83a0` 的旁路，最终到 `0x4e8440`，这条旁路没有 `0x4e8111` 写入。
2. 在公共尾段 `0x4e808d`，`DWORD[action+0x34] == 0`。若非零，`0x4e8090` 跳到 `0x4e8333`，跳过日期字段处理。
3. action vtable `+0x98` 的前 3 次返回值不能分别命中 `0x293d`、`0x331d`、`0x3320`。命中任一值会转到 `0x4e8119`，写的是 `country+0x2494`，不是 `+0x24a0`。
4. 第 4 次 `+0x98` 调用在 `0x4e80ce` 返回 `0x293c`。若不是，`0x4e80e0` 跳到 `0x4e814e`，不写 `+0x24a0`。

因此，“法国的 last 值没有更新”至少可以由三类情况解释：`+0x80` 失败、`action+0x34` 非零，或 `+0x98` 最终没有给出 `0x293c`。如果命中前三个特殊返回值，动作可能写了另一个槽 `+0x2494`，仅看 `+0x24a0` 会误判为没有处理。

## `+0x100` 与状态字段的影响

`0x4e7cb6` 调用 action vtable `+0x100`。这里需要区分两条路径：

- 当最初的 `+0x80` 返回假时，`0x4e7cb0` 跳到 `0x4e83a0`；此旁路不会进入 `0x4e808d` 的日期写入段。
- 当 `+0x80` 返回真时，`+0x100` 返回假只使 `0x4e7cbe` 跳到 `0x4e8023`，随后仍可到达 `0x4e808d`。所以从这个函数的可见控制流看，`+0x100 == false` 本身不是 `+0x24a0` 的硬阻断；是否写入仍由 `action+0x34` 和 `+0x98` 返回值决定。

`action+0x34` 在 `0x4e7cca` 读取：

- `0`：继续普通路径，最终可能执行上面的 `+0x24a0` 写入。
- `2`：在 `0x4e7e53` 还会调用 vtable `+0xf8`；若其返回真，直接到 `0x4e7ed1`。无论后续是否继续到公共尾段，`0x4e8090` 都因状态为非零跳过日期写入。
- `1`：从 `0x4e7e6e` 进入另一条状态处理；最终到公共尾段时同样因 `action+0x34 != 0` 跳过 `+0x24a0`。
- 其他非零值：`0x4e7e69` 转到 `0x4e7ed1`，公共尾段仍由 `0x4e8090` 跳过日期写入。

这只说明控制流与字段值的关系，不把 `1/2` 命名为接受、拒绝或其他业务语义。

## `+0x208=1` 和“100%战争分”

在 `0x4e7c80` 的可见指令中没有读取 `action+0x208`；`RVA 0x59b480` 的 `+0x80` 实现也没有直接读取该偏移。`+0x80` 会检查 action 的参与方、战争/关系记录、条款集合，并调用 `0x59ae30`、`0x981b90`、`0x4ebde0` 等验证逻辑，因此战争分或条款状态可以间接影响其返回值，但在这两段反汇编中没有“100%战争分”或数值 `100` 的直接分支。

`RVA 0x59bf10` 是发送前预览路径；`0x59bf88` 检查 `action+0x208`，在该标志非零且 `r8b==0` 时于 `0x59bf97` 返回 `0x3e8`。发送回调据此把预览结果映射到 `action+0x208=1`，克隆 action 也会复制这个字段。已确认的结论是：`+0x208=1` 会改变预览/发送前路径，但不是 `0x4e7c80` 中直接阻止 `country+0x24a0` 的门槛。若第二轮日志显示 `preview=100`、`+0x208=1` 而 last 不变，应优先记录 dispatch 时的 `action+0x34`、`+0x80` 返回值以及四次 `+0x98` 返回值；仅凭 `+0x208=1` 不能判定动作被执行器拒绝。

## `BRIDGE_DISPATCH_DIAGNOSTICS` 增量复核

新增块位于 `work/native/probe.cpp:270-292`，只在 `send && wrapped` 且定义了 `BRIDGE_DISPATCH_DIAGNOSTICS` 时执行。它读取 clone 的 `vtable+0x80`，确认槽值为 `base+0x59b480`，保存 `clone+0x34`，然后以 `RCX=clone、RDX=nullptr、R8=0` 调用该方法。这与 `0x4e7c80` 的首个 gate（`0x4e7ca1`，先清零 `EDX/R8D`）一致；Win64 返回值在 `AL`，`bool` typedef 与现有 `test al` 用法相符。该方法的反汇编将第二参数保存为 `r14`，第三参数在本体中没有被使用，因此当前 `void*, void*, unsigned char` 原型没有发现 ABI 阻塞问题。

生命周期路径也闭合：诊断发生在 `Wrap` 完成后、`Submit` 之前，clone 仍由 command 持有；调用后再次读取 `clone+0x34`，若身份、原生返回值、状态读取或状态保持为 0 任一失败，设置 `wrapped=false`，不调用投递器。随后 `command` 仍为未提交指针，由已有 `0x4e74a0(command,1)` 正常销毁；若进入投递器，`0x14ca110` 会先清空指针容器并自行处理/销毁其本地 command，外围代码不会重复销毁。没有看到新增的提前释放、悬挂 clone 或重复析构路径。

保留两个非阻塞边界：`flag_208` 在日志中直接从已通过包装/虚表检查的 clone 读取，当前对象有效性链足以支持这次同步诊断，但它不是 `read()` 失败可观测项；此外，预检调用 `+0x80` 仍可能让内部验证函数执行两次（预检一次、真正执行器一次），静态反汇编未见该 gate 修改 `action+0x34` 或 `+0x208`，不过时间敏感的外部状态变化仍不能由此排除。当前增量未发现阻塞性 ABI 或生命周期缺陷。

验证：只读复核 `probe.cpp` 新增块、`peace-action-validity.txt`、`peace-repeat-4e7c80.txt`、`peace-command-destructor.txt`、`peace-dispatch-14ca110.txt`；并核对 `work/native/eu4_bridge_dispatch_v1.dll` SHA-256 为 `0C031D88DF66C87DEFD9A534928441E3FF49C4BBF88BDD7BB56525EF7081D70C`。未修改源码、未注入、未发送动作。

## 当前结论与验证边界

已确认 `+0x24a0` 的唯一写点、其前置分支及对应的 action/actor 槽位。尚未从本次窄审计中恢复 `+0x100` 或 `+0x98` 的完整业务语义，也没有把 `preview=100` 解释为接受/拒绝。要区分第二轮测试的实际失败点，需要在不改行为的情况下记录上述门槛的返回值；只看最终 `last` 字段不足以定位。
