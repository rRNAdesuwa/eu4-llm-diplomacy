# EU4 1.37.5：战争绑定的议和参数与零条款状态

本轮已闭合参数构造、当前国家对的战争查找、谈判方向、参与国生成，以及正常界面的重置条款路径。**默认空 `CPeaceOffer` 不是白和平；正常战争参数构造也不是空容器，它会保留一个已选中的零金额 `po_gold` 组件。** 本文只有静态证据，没有调用构造、预览、重置、发送或游戏进程接口。

精确 EXE SHA256 为 `9ad3efe1af169f40ee577f9dae5debbc87af6fb8b5450fb345ebf110dc4d771a`。所有地址均为 RVA。机器证据见 [native-peace-parameters-1375.json](../work/reports/native-peace-parameters-1375.json)，可复现生成器为 [trace_peace_parameters_1375.py](../work/trace_peace_parameters_1375.py)。报告固定已有 owned-peace、GUI send、action fields 三份报告及解包的 `interface/peaceview.gui` SHA；每条结论的 `facts.*.instructions` 保留地址、原字节和来源，所有借用旧报告的指令都会重新与精确 EXE 核对。

## 构造参数：谁提出，与谁给付，分别保存

`975d40` 是在未构造的 `0x1c0` 存储上执行的原生构造函数。寄存器含义来自实际写入和正常 GUI 调用者：

| 输入 | 原生字段 | 证据 |
|---|---|---|
| RCX | 目的对象地址 | `975d5d`，最终 `975f1a` 返回自身 |
| RDX | taker 完整 8 字节国家 handle，写 `+18` | `975d75` |
| R8 | giver 完整 handle，写 `+10` | `975d71` |
| R9B | `is_demand`，写 `+20` | `975d79` |

设 A 为发起国，B 为收件国。GUI 的两种正常构造不是单独翻转一个布尔值：

| 谈判方向 | 调用 | giver / taker | GUI 中的完整 offer |
|---|---|---|---|
| 提出要求 | `975d40(dst, A, B, true)` | B / A | `GUI+48` |
| 提出让步 | `975d40(dst, B, A, false)` | A / B | `GUI+208` |

两种方向的外层 request 始终是 actor=A、recipient=B。正常调用者 `13067b0` 的依据分别为 `1306863..1306871` 与 `1306962..1306970`。它也可能从 `GUI+3c8`、`GUI+3e0` 的两个缓存向量深拷贝旧 offer；缓存元素步长 `0x1c0`，目标匹配仅比较国家 slot。因而直接复制 GUI 当前对象，可能带入用户之前选中的条款，不能声称已得到零条款提案。

参数构造顺序为：原生拥有式容器初始化 `2c67a0` → `97bea0` 参与国 → 40 个类型索引桶 → `978cd0` 辅助状态 → `97ed00` 候选条款。没有 war 指针、war ID 或日期参数。外层日期另由 GUI send 读取 `game+1dd0`，传给 `598af0`，写在 request `+28/+2c`；正常 wrapper 会刷新克隆的 `+2c`。

## 真实战争来源：当前关系索引返回借用指针

`97bd30` 的完整查找只有几十条指令，已逐条收录：

1. 从 `offer+18` 取 taker handle，执行 `signed16(handle >> 32)` 得到国家 slot；通过全局 `233d8d0` 的 database `+118` 国家指针数组取得 taker 对象。
2. 同样取 giver 的 slot，在 `taker+1510` 的关系表选择 `giver_slot * 0x48` 项。
3. 该关系项 `+0` 是关系 root，`+10` 是另一端的完整国家 handle。取后者的 signed slot 作为查找 key。
4. 遍历 `root+50` 指针及 `root+5c` 有符号 DWORD count 表示的数组。每项 16 字节，`+0` DWORD 是上述国家 slot key，`+8` QWORD 是返回的战争指针。取第一个匹配项；无匹配返回 null。

`28d990(root+48, counterpart_handle)` 是同一布局的通用查找；议和文本生成 `9851f0` 通过它再次取得战争。request 合法性 `59b450` 还会从 actor→recipient 关系独立重新查一次。**这个索引 key 是国家 slot，不是公共接口中的数字 `war_id`。** 本轮没有找到一个已验证的稳定、全局唯一、可序列化的 war identity 参数。

`CPeaceOffer` 在这些构造/拷贝路径中不保存一个拥有式战争指针。它保存国家和条款的快照，后续还会按当前关系查战争。旧 offer 的深拷贝不能锁定旧世界中的那场战争。战争对象的最终拥有者、删除同步、多战争重复 key 的处置规则、原址复用和 world epoch 仍未闭合；不能用指针相等或日期相等代替这些证明。

这些原生查找也没有完成对公共输入所需的所有保护：没有数组上界检查、完整 handle 身份相等检查、唯一 key 检查或世代固定。将裸 TAG/slot 直接传给它们并不安全。一个未来只读观察器至少要先独立核对完整 handle、当前数据库/数组、索引边界及重复项，再核对战争两侧；这只是观察设计，不是本文实现的接口。

## 战争全体成员与实际谈判成员

报告保留 `war+48` 和 `war+78` 为“侧 A”和“侧 B”，不凭这一组切片强行命名为 attacker/defender。

`97bea0` 先测试 taker slot 是否在侧 A 的 8 字节 handle 向量中：在则 `offer.war_takers+40` 深拷贝 A、`war_givers+28` 深拷贝 B；不在则方向相反。随后构造实际谈判成员：

| 字段 | 当谈判国等于本侧向量首项 | 否则 |
|---|---|---|
| 实际 takers `+70` | 加入该侧全部成员 | 加入 taker 自己及同侧满足条件的直属属国 |
| 实际 givers `+58` | 加入该侧全部成员 | 加入 giver 自己及同侧满足条件的直属属国 |

直属属国检查涉及国家 `+18f0` 的 overlord handle、关系 root 的 dependency 索引 `+128/+134`、dependency `+40` 的定义及定义 `+121` 非零。实际插入的是完整 handle，角色判断仍大量采用 slot 比较。这里只证明原生“向量首项”的谈判角色分支，没有证明所有战争类型的唯一战争领袖语义；空侧向量等非法对象也不能直接交给构造函数。

如果找不到战争，`97bea0` 仅向实际 givers 加入 giver，`97ed00` 随后直接返回。构造返回非空、vtable 正确、容器已初始化、甚至 `+1b8=1`，均不能据此认定战争绑定成功。

## 候选池、选择索引及正常白和平形态

`offer+88` 是拥有组件对象的候选指针向量。`+d0` 是 40 个类型向量组成的索引，里面的指针只是候选对象的别名。`+a0/+b8` 还是有效选择计算中的附加/移除集合；`97b8a0(..., true)` 会把它们合并。只数候选池、只读 component `+20`，或只看一个类型桶，均不足以覆盖带这些附加集合的对象。

`97ed00` 会调用 `97cda0/97d130/97d4e0/97e1f0/97e500/97db60` 等生成候选。其直接候选初始化写 component `+20=0`。但最后的 `981089..981112` 有特殊步骤：

- 分配 `0x38`，安装 `po_gold` vtable `1cd2440`。
- component `+10/+18` 保存 giver/taker，未对齐 `+22` 保存受影响国家 handle。
- DWORD `+30=0`。
- 调用 `97a790`，把 component `+20` 改成 1，放入类型 0 桶，并通过 virtual `+118` 更新 offer 辅助状态。

生成器对最后的金额写入做了直接 CFG 的向后定义检查。所有可能到达 `9810c6` 的 R15 定义恰为 `9803c5/980453/980b90` 三处 `xor r15d,r15d`；不是只看最近一条汇编就猜金额。该检查仍依赖 Windows x64 非易失寄存器 ABI，没有执行游戏代码。

正常“重置”按钮的原始 GUI 定义在 `peaceview.gui:422`。绑定链为 `GUI+3f8` listener → 回调 `1306a10` → 根据 `GUI+660` 选择方向对象 → `97ae50`。它枚举已选组件，保留 descriptor `(type=0, definition=null)` 的金额组件，对其他条款调用 `97a8d0` 取消选择，然后 `97b390` 把金额置 0，并用组件虚函数撤销/重算辅助数据。它没有把拥有组件的向量整体清空，也没有释放所有候选。

`981b30(offer, false)` 是与白和平显示直接相连的原生判定：先读有效金额，正值拒绝；再按 registry `242bd80` 枚举有效已选条款，仅容许 type 0。其第二参数为 true 时另允许 type `0xb`，本文不把那个变体当作普通白和平。`985345` 以 false 调用该判定，正常文本分支在 `98565a` 引用 `WHITE_PEACE`；另有依赖 `war+18` 的特殊文本分支，因此本文只声称谓词与显示的关系。

比该谓词更保守、可供下一轮观察的最小形态是：**恰好一个有效已选的 type 0/definition null 金额组件，值严格为 0，没有其他有效已选条款，所有拥有式容器和别名关系仍由原生函数维护。** 原生金额读取在匹配数量不是 1 时也可能返回 0，谓词亦只拒绝正金额；不能利用这些宽松情况接受结构异常的对象。

## 下一步能够审阅的参数合同与尚缺条件

未来候选需要显式固定 A/B 完整身份、方向、当下存在的战争索引对象、两侧与实际谈判成员，使用正常参数构造和拥有式拷贝，并验证上述零条款形态。日期属于外层 request。源 offer、request 内嵌 offer、command 拥有的克隆 offer 是分别管理的对象，不能互相借用容器指针；战争指针则是当前世界中的借用对象。已有生命周期报告的默认空对象自检，只覆盖拥有式构造/复制/析构，不能自动升级成战争参数自检。

`59b450` 和 `59ae00` 还有独立的合法性条件。新报告收录了原生拒绝文本及其字节锚：无战争、无条件投降、属国/宗主/包围网禁止单独议和、从属方不能议和、继承战争单独议和限制，以及后续条款/省份条件和基础外交合法性。零条款不等于合法；合法不等于 AI 接受；context 返回与真正和平生效、保存重载更不是同一证据。

参数构造的候选生成器会深入国家、战争、脚本及虚函数调用。**本轮没有证明所有传递调用都是只修改临时 offer 的纯操作，也没有闭合异常分配展开。** 因而不能仅以“没有发送”宣布参数化构造已经安全可运行。`97a670/97a8d0` 的间接 switch 分支仍显式列在报告中；`9851f0` 只解码与白和平判定相关的首 `0x6a0` CFG，不假称完整覆盖文本生成。没有编写 sender、没有强制 AI、没有公开 force 或任意 war 指针。
