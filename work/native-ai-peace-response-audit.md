# 原生 AI 接收方和平响应窄审计

日期：2026-10-04  
版本：EU4 1.37.4  
文件 SHA-256：`b23fa0e1f698d31b01cdd1c3817a675805d8c6286cb66f9c231e6e2a42544d77`

本记录只做离线 PE 反汇编和调用关系检查，没有注入、没有写入游戏进程，也没有把预览结果当作实际响应。地址均为 `eu4.exe` 模块 RVA。

## 598f00：实际和平结算候选

动作虚表位于 `0x1c7b840`。`0x598f00` 是该虚表的 `+0x48` 槽；它不是已经验证过的通用发送入口。

在 `0x598f00` 内：

* `action+0x34` 被分成 `0`、`1`、`2` 三条状态分支（`0x59951b`）。
* 经后续完整控制流复核，`+0x34 == 1` 分支不会到达 `0x59a716`；此前将其归为结算路径的判断错误，已更正。
* 到达 `0x59a716` 时，`RCX` 是 `action+0x48`，随后直接调用 `0x9765a0`。该函数由 PE 字符串 `CPeaceOffer::Execute, %d` 标识，并且是本版本唯一找到的直接调用点。
* `+0x34 == 2` 从 `0x599bb8` 进入另一条响应路径。状态0/2后续路径存在通往`0x59a716`的汇合边，是否执行仍受其他条件约束；此前受限反汇编的否定判断不成立。详见`native-response-state-branch-audit.md`。

因此，`598f00 → 9765a0` 是真实执行和平条款的强证据，而不是 UI 预览。仅凭无符号反汇编，还不能把 `+0x34 == 1/2` 命名为接受/拒绝；结合函数候选字符串 `PEACEREJECT`、`PEACEACCEPT`、`peace_accepted`，最合理的工作假设是其中一条为接受、另一条为拒绝，但仍需一次游戏内结果确认。

现有发送命令执行器 `0x4e7c80` 直接调用动作虚表的合法性、类型、日期等槽位，并在白和平发送成功时更新 `country+0x24a0`；它没有在该函数内直接调用 `598f00` 或 `CPeaceOffer::Execute`。所以“命令已入队”或 `+0x24a0` 前进，只能证明发送动作通过了部分执行路径，不能证明接收方已接受。

## 59bf10：不是 AI 响应接口

本轮确认 `0x130c150` 有直接调用 `0x59bf10` 的 UI 路径；不能据此认为它是唯一调用点，因为另有已验证的发送回调通过动作虚表+0x120调用同一函数。页面路径准备理由向量并按返回值更新页面；发送回调则据返回值设置动作+0x208。两者都不足以证明接收方已作出实际响应。

`59bf10` 的开头还存在一个玩家/观察者相关的特殊分支：在全局状态满足条件、动作参与者与当前玩家或观察者句柄相符时返回固定高值；另有 `action+0x208` 和调用方 `r8b` 的快捷返回。否则它把 `action+0x48` 交给 `0x1bf180` 进行复杂计算。这里能证明“页面预览会区分某些玩家状态”，不能证明它就是 AI 接受决策，也不能证明它覆盖了接收方响应。

因此，`59bf10` 的返回值不应作为 AI 接受或拒绝的观测信号；父桥接中的 `preview_raw` 也不应被解释为最终响应。

## 最小人工验证

在玩家国家改为 POR、FRA 和 ENG 仍处于战争、FRA 由原生 AI 控制的存档上：

1. 通过当前已验证的桥接发送固定的 FRA→ENG 无条件和平；保存发送前存档。
2. 保持暂停查看是否立即出现 AI 响应；若没有，解除暂停推进 1–3 天，再暂停。
3. 玩家POR可观察战争是否结束、停战是否生成；不能要求作为AI的ENG由用户打开并点击通知。若测试赔款，再用存档核对ENG国库变化。
4. 战争继续本身不能证明AI已拒绝，也可能是尚未响应或请求失效；拒绝验收必须有明确响应通知或可核对的响应状态码。重复相同状态和条款也不保证能同时测到接受与拒绝。
5. 若 `game.log` 出现 `PEACEACCEPT`、`PEACEREJECT`、`peace_accepted` 等消息，可作为响应分支的辅助证据；这些字符串目前只证明日志/消息资源存在，不能单独证明某次动作已经执行。

POR在既有战争中是英方盟友。临时由玩家控制POR的作用是让当前玩家句柄不等于FRA/ENG，并让ENG交还原生AI；不能据此断言完全避开全部玩家或盟友相关计算。FRA→ENG的接收与结算仍须通过原生引擎验证。成功判据是战争结束、停战及原生后果；单独看到submitted、预览分数或发送日期变化都不够。

## 当前结论与边界

静态证据已经把“接收后真实结算”的候选收窄到 `598f00` 的状态分支和 `9765a0`，也确认 `59bf10` 只是原生和平页面的计算/刷新路径。尚未定位一个可从只读内存直接读取的“AI 接受/拒绝布尔值”，也没有证据表明 `598f00` 可安全地从外部线程调用。下一步只需完成上面的 POR 场景人工验证，再决定是否为桥接增加响应状态记录；不要把 `preview_raw` 或 `submitted` 改名为接受结果。
