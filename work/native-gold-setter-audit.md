# 原生议和金币控件静态审计

## 后续校正与测试准备

**首版实测后的单位修正：** 0x97b3a0 不是“输入金额→裁剪金额”，而是以内部战争分数预算换算金币金额。0x130f270 普通加号路径传1000，结果作为金币增量传给中央更新；后者用100000获取金币上限，做金额裁剪和100单位精度取整再调用setter。实测传1000输出34400，首版在setter之前因错误的等值要求停止，未发送。金额条款+0x30与条约费用汇总+0xf0是不同单位，不能强制二者相等。证据 native-gold-step-exact.txt、native-gold-ui-update-exact.txt、native-gold-limit-complete.txt 及 native-gold-v1-lifecycle-rejection.json。下文早期“请求目标内部步进1000并要求条款与汇总均为1000”已被此修正取代。

复核 0x13116e0 的精确反汇编：RCX 取 window+0x48 或 +0x208，即 CPeaceOffer，不是独立控件。因此 0x97b130、0x97b200、0x97b3a0 应描述为条约级金额读取、写入与上限计算方法；前文的 control/绑定层措辞不够准确。

原生页面调用 0x97b3a0(offer, out RDX, input R8)，然后把裁剪和取整后的目标值指针传给 0x97b200(offer, value RDX)。后者查找条约内部金额条款，先调用其虚方法 +0x118（R9B=1），更新条款+0x30，再调用同一方法（R9B=0）；两次调用使用条约+0xe8 owner 及条约+0x20 方向。0x97b130 同样查询该条款并读取 +0x30。这样可以复用条约级方法，不必创建或操作和平窗口，也不裸写 +0xf0。

新测试版请求目标内部步进1000，由原生上限函数裁剪；若结果不是1000则不继续。调用原生 setter/getter，要求条款读回值和条约+0xf0汇总均为1000；再调用原生费用计算候选0x978ed0，记录原始整数，不把它直接称为金币或战争分数。发送仍经过完整构造、参与国、深复制、按钮预览与投递检查。具体币值和结算尚待实测。

注意 PE 异常表可能把一个函数的序言和后续代码分成多个范围。0x97b3a0 的首范围只到0x97b3ca，后续仍有金额上限计算；不能仅用该首范围判断函数结束。本文早期边界是观察范围，不保证完整函数覆盖。

审计对象：EU4 1.37.4 `eu4.exe`，SHA256 `b23fa0e1f698d31b01cdd1c3817a675805d8c6286cb66f9c231e6e2a42544d77`。
所有地址均为模块 RVA；函数边界来自 PE `.pdata`，没有注入、没有修改 `probe.cpp`。

## 已确认的控件更新链

原生议和窗口附近有四个小回调，`.pdata` 边界和共同调用如下：

| RVA 函数边界 | 已见行为 |
|---|---|
| `0x130f270–0x130f399` | 读取当前控件值，构造负/正变化量，调用 `0x13116e0`；随后用 `0x978ed0`、`0x97b3a0` 做边界处理 |
| `0x130f3a0–0x130f473` | 读取全局步长/上限 `0x14233dba0`，乘 `0x3e8` 后减当前值，经 `0x97b3a0` 后调用 `0x13116e0` |
| `0x130f480–0x130f584` | 先调用 `0x1311540` 生成/计算一个完整议和动作，再经 `0x97b3a0` 和 `0x13116e0` 更新控件 |
| `0x130f590–0x130f617` | 读取当前值或默认步长，经 `0x97b3a0` 后调用 `0x13116e0` |

四个函数都按窗口方向标志 `window+0x660` 选择 `window+0x48` 或 `window+0x208` 这一侧的控件。现有静态证据不能安全地把上述四个函数分别命名为金币加号、金币减号或其他条款按钮；它们应视为“条款数值控件回调”。

### 中央更新函数

`0x13116e0–0x13117d8` 的可见 ABI 是：

```text
update(window RCX, ignored RDX, delta_or_target R8 -> int32)
```

证据：

- `window+0x48` 或 `window+0x208` 经 `0x97b130` 读出当前 `int32`；
- 与 `[R8]` 相加；
- 以 `0x97b3a0(window-control, &100000, &out)` 做非负/上限裁剪；
- 变化时调用 `0x97b200(window-control, &new_value)`；
- 随后调用 `0x1306930(window, *(window+0x28))` 和 `0x1308ff0(window)` 刷新议和页面及相关结果。

因此，若要复用原生金币加减逻辑，优先级最高的候选是让已有窗口控件回调或 `0x13116e0` 运行，而不是直接写 `CPeaceOffer+0xf0`。直接改 `+0xf0` 的刷新要求尚未证明。

## 绑定层与条款对象

函数边界：

- `0x97b130–0x97b1f7`：从控件绑定对象读取 `int32`；输出指针在 `RDX`。
- `0x97b200–0x97b302`：向绑定对象写入目标值；输入形态为 `control RCX, int32* RDX`。值变化时，它从绑定对象取得底层对象，并调用该对象虚表 `+0x118`，同时传递绑定对象的方向/上下文字段。
- `0x97b3a0–0x97b4bf`：按全局金额比例、国家相关上限和传入上限计算并写回 `int32* RDX`；回调中用于裁剪候选金额。
- `0x1311540–0x13116da`：创建一份完整外交动作，并通过 `0x975db0` 深复制 `CPeaceOffer`，用于数值/合法性计算；它不是已确认的金币字段 setter。

这说明原生页面的金币调整至少经过“控件绑定 → 条款对象虚方法 +0x118 → 页面刷新”，而不是简单把页面上显示的数字写入 `CPeaceOffer+0xf0`。现有回调中没有发现对任意寄存器基址加 `0xf0` 的直接写指令。

## 与已知金币步进观测的关系

运行时原生页面观测到：`CPeaceOffer+0xf0` 从 `0` 到 `1000`，页面显示 `25.6` 金币；再到 `2000`，页面显示 `51.2` 金币。静态代码中的多个 `imul ..., 0x3e8` 与上述内部整数步进一致，但不能单独证明金额换算在所有战争分数区间均线性。

## 尚未确认项

1. 哪一个 `0x130f270/0x130f3a0/0x130f480/0x130f590` 正好对应金币加号；需要结合控件绑定注册或一次受控 UI 事件确认。
2. `0x97b200` 所调用的底层虚表 `+0x118` 的具体类和参数语义；目前只能确认它是绑定写回入口。
3. `CPeaceOffer+0xf0` 的最终写入点及写入后的所有派生字段刷新；没有证据支持只改 `+0xf0` 后直接发送。
4. `0x97b3a0` 的国家上限/比例计算已能从指令确认，但其全局字段含义和完整取整规则尚未完全命名。

结论：当前最可靠的原生赔款实现路线是定位金币控件对应的现有回调，或在同一游戏线程调用 `0x13116e0`，让 `0x97b200` 和后续两个刷新函数完成引擎写回；不能把裸写 `+0xf0` 当作等价实现。
