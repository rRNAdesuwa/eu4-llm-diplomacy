# 1.37.5 单人来源增量：context 与平台回退

本轮闭合了 context `+54/+55` 的两个构造路径和 SP Play 的 Steam／平台回退分支，并找到了能在同一个 context 地址上更换 transport 的转换函数。可据此设计具体的原生消费检查和授权撤销入口；**尚未部署来源见证或验证运行覆盖，生产执行继续为 0。** 没有访问进程、注入、发送请求或修改冻结文件。

新增脚本 `work/trace_single_player_context.py` 及报告 `work/reports/native-single-player-context-1375.json`。报告 SHA256：`0943d8f4b142daf260cbc4ea407fe4b05d6ad9898aa6c40ba44dc25788162bbf`。它哈希绑定上一份 `native-single-player-origin-1375.json`，直接引用其中的 Play 分支证据，没有重跑上一份完整的 95 个锚点。增量解码 15 个函数，另检查两个限定区域的 300 个 pdata 函数；包括重叠总计 121,448 字节，报告 472,111 字节。

## 两个标志的确切来源

context 两个构造函数 `14c83e0`、`14c8940` 都安装虚表 `1d8c900`，先将 `WORD [context+54]` 清零。随后按 context 类型设置标志：

| 类型 `DWORD +4c` | `BYTE +54` | `BYTE +55` | transport 构造函数 | transport 虚表 |
|---:|---:|---:|---|---|
| 0 | 0 | 0 | `157b5b0` | `1d96268` |
| 1 | 1 | 0 | `15764d0` | `1d96088` |
| 2 | 0 | 1 | `157ffe0` | `1d96178` |

配置构造函数 `14c83e0` 从输入配置 `+a0` 取得类型；另一构造函数 `14c8940` 使用第 4 个参数，再调用 `14c97e0` 初始化。transport 保存在 context `+58`；初始化器写入反向链接 `transport+70=context`。这使原生线程可以核对对象及类型的一致性。

`+54/+55` 并非 SP / MP 的两个互补开关。正常的 Steam 可用 SP Play 分支给配置构造函数 `1558f00` 的第 6 个参数传 1；它将 1 保存到配置 `+a0`。因此类型 1 也存在于 SP 配置路径。只允许 `+55=1` 会漏掉这条合法来源；只允许 `+54=1` 则无法排除网络 host 类来源。

本轮检查了 `[14c8000,14d6000)` 中 215 个函数的明确 `mov` 写入。已归属 context 的写入只有两个构造函数、初始化器 `14c97e0` 和下面的转换函数 `14cd8b0`。另外检查 `[1575000,1582000)` 的 85 个 transport 函数：其中 `157f644` 的 WORD `+54` 清零属于刚分配的 `0x58` 字节 helper，不是 `0x880` 字节 context。报告保留全部候选写入及排除证据；这个范围明确的清单不冒充全程序或间接／批量写入完整性证明。

## Steam／平台回退已解析

`1120dd0` 的回退条件是 `!SteamAPI_IsSteamRunning()`，或选中的平台对象 `+8==3`。前端模式为 0 且回退条件成立时，它：

1. 通过 server 虚槽 `+88` 清空旧 context。
2. 调用 `113b350`，传入类型 2、端口 `0x29a`。该函数使用 `localhost` 和 `Launch` 字符串，调用 `14c8940` 构造类型 2 context / transport。
3. 再通过虚槽 `+88` 安装新 context。

运行 server 与前端控制对象的这个虚槽均为 `811ab0`。它读取 `server+330` 的 holder，将输入 owning pointer 移入 `holder+370`，清空输入指针，并调用旧 context 的虚析构。这是具体的 context 替换入口。

回退分支没有重设 `controller+400` 的两个配置字节。因此不能把“回退创建了类型 2 context”当作自动消除旧网络来源的证明。如果它带入的配置不是 `(1,0)`，来源见证直接拒绝；不要修改游戏字段修正它，也不要仅凭新的 transport 自动重新授权。

## 固定来源见证可以排除的反例

新 production 宿主可以维护不可由请求传入的 `origin_witness`。见证应记录一次实际被宿主观察到的 SP Play 序列：前端模式 0、最终复制配置 `(1,0)`、确切平台分支、新 context 的创建／安装及运行 server 构造，绑定 adapter 自有 epoch。仅在中途附加到已运行世界时采样到这些字段，不足以创建见证。

原生主线程每次消费前至少核对：

- 完整构建与会话身份、有效且未撤销的 epoch / origin、暂停、线程和当前玩家身份。
- `game+747c=0`，`game+1e00` 的实际运行 server 虚表为 `1cb8460`，`server+19f0/+19f1=(1,0)`。
- `server+330 -> holder+370` 的 context 身份和虚表 `1d8c900`，`context+58` transport 身份及其 `+70` 反向链接。
- context 类型／标志／transport 必须严格符合上表的类型 2 或经单独验收的 Steam-SP 类型 1 组合；类型 0、非规范布尔、组合不一致一律拒绝。
- 有界玩家链只包含本地 ID，最多 256 节点；读取失败、环或超限拒绝。这个检查是附加条件，不能替代来源。

此前“网络配置 `server+19f1=1`，但只有本地玩家，所以分类器返回 false”的反例会被配置检查直接拒绝；前端控制对象的无条件 false 会被运行虚表检查拒绝。SP 回退带入旧配置也会拒绝。这些是明确定义的收紧，不依赖对未知字段起一个可信名称。

## 必须在入口撤销，不能等快照变化

| 入口 | 已确认行为 | 宿主动作 |
|---|---|---|
| `811ab0` | 清空／替换 `holder+370`，可析构旧 context | 进入即撤销 origin 和待执行请求；仅预期的 SP 构造序列能创建新见证 |
| `14c9930` | 关闭／重初始化现有 context，使用原有 `+4c/+58` | 进入即撤销，不能沿用地址恢复授权 |
| `14c97e0` | 写入类型、标志、transport、反向链接；只设置匹配标志，不清另一标志 | 对已绑定 context 的调用必须撤销；首次构造只能进入候选状态 |
| `14cd8b0` | 保持 context 地址，写 `+54=1`，析构旧 transport，再构造类型 1 transport；另一分支构造类型 0 transport | 在通知和修改之前撤销，禁止通过“context 指针没变”绕过 |
| `74b8a0` | 既有报告中的 load/reset 入口，包括失败加载 | 世界 epoch 在修改前撤销，读档成功也不自动重新授权 |

`14cd8b0` 由 `14ca360` 的两个已验证直接调用点进入。它不会同步修改 `context+4c` 或清除 `+55`；所以单独依赖类型值也会过时。`14c9930` 再初始化可能保留原来的标志，进一步说明必须核对组合并监听入口，而不是只在每帧读一个 bool。

上表收敛了本轮模式来源问题的具体实现边界。世界清理入口的完整性由独立 world-epoch 研究继续验证；这里没有把同地址、同日期或这几个 session 入口冒充全部世界生命周期覆盖。正式启用前的增量验收只需针对上述两种确切 profile 和来源序列做只读观测、验证这些入口确实先于修改撤销，再审核新宿主实现。未观察到的启动／构造／转换分支保持拒绝，不扩展成后验猜测。
