## 两个状态字节都不是世代计数

`74a260` 在 `74a289` 写 game `+0x7485=1`，在 `74b1e8` 写回 `0`。它还在 game `+0x74c8==nullptr` 时清 game `+0x7480`；加载路径因为先设置了 `+0x74c8`，不会走这个清位分支。

因此 `+0x7485` 可作为正在重置的辅助观察字节，`+0x7480` 可作为状态观察值，但它们都不是单调增长的读档计数。逐帧采样可能完全错过一次置位再清零；不能据“两个采样值相同”认定中间没有换世界。

取消改善关系的析构会检查 game `+0x7485`，与重置期间不按普通规则召回外交官的路径一致。这里能确认读写行为，尚不能为所有清理上下文命名。server 虚槽 `+0x140` 也已解为 `802540`，只读取 server `+0x1158` BYTE；其完整含义未知，不是已证明的单机标记。

## 原生多人分类函数及它的局限

`6eaa10(server)` 确实是原生多人分类函数：`81b50b` 调用后选择字符串 `multiplayer` 或 `standard`；存档 serializer `74f41b` 调用后以 token `0x3329` 保存 `multi_player`。

但其具体算法并非简单“是否创建过联网会话”：

1. 调用 server 虚槽 `+0x318`。当前 pinned vtable `1cb8460` 对应 `80ff80`，读 server `+0x19f1` BYTE；false 时返回 false。
2. 使用 server 虚槽 `+0x80=811aa0` 取 context：`*( *(server+0x330) +0x370 )`。
3. 如果 context `+0x54` 与 `+0x55` 都为零，返回 true。
4. 否则遍历 game `+0xa50` 链表，比较每个节点 `+0x18` DWORD ID 与 context `+0x8c` DWORD ID；遇到不同 ID 返回 true。
5. 链表为空或所有 ID 相同，返回 false。next 指针在 node `+0x60`。

这个公式可作为只读分类的明确静态依据：读取器应验证所有指针、限制节点数量并拒绝环链和不可读值，不必为了分类而调用游戏函数。但它的 false 分支并没有独立证明“纯离线来源、不存在可加入的 MP host 会话”。尤其玩家数量/ID变化会影响结果。server `+0x19f1` 的全部设置路径和会话来源转换尚未建立，所以也不能把单独 `+0x19f1==0` 宣布为已验证的严格 SP gate。

同一个 context 被本地提交路径和该多人分类函数使用。context `+0x55/+0x80d` 可提交状态、transport vtable、server vtable 都不能替代严格单机身份验证。

## 下一轮可以做什么

下一轮应先做独立的无发送生命周期观察，在候选入口 `74b8a0` 以及必要的更早 UI/世界重置边界记录进入事件，确认每种界面入口、同存档重复加载、失败加载、新游戏、返回菜单和实际存在的联网转换，均在任何旧请求被消费前触发撤销。若一种路径只更换进程，PID 加进程创建时间可拒绝旧握手，但不能据此推断全部路径都重启进程。

adapter 自己维护原子递增 epoch 是可行的设计方向。经证实的入口一旦进入，应先递增 epoch、撤销会话、清理待处理请求，随后才允许游戏继续；失败或异常后也维持撤销。候选入口重复命中导致 epoch 多增不会影响“旧请求必须拒绝”的原则。原生游戏字节不应改写为计数器，加载结束也不应自动恢复旧 session。

只有新的地图状态、线程、国家身份、严格单机前提和一份新握手重新确认后才能重新授权。独立验证 hook 的覆盖与线程行为之前，正式 mailbox 的 `world_generation` 仍是明确未完成条件。本报告没有提供可直接上线的世代 hook，也没有把当前候选提升为生产级安全保证。
