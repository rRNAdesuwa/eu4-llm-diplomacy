审计范围：`work/native/frame_stub.S`、`work/native/probe.cpp` 的响应虚表观察桩、安装/失败路径。本文是静态审计，未把 `state_raw` 映射为接受或拒绝，也不把观察桩的存在当作响应结果。

## 结论

在当前审计范围内，正常安装与正常调用路径的 ABI 转发设计成立：观察桩保存并恢复原始的易失整数寄存器、`XMM0–XMM5` 和标志寄存器；不改变原始栈参数；恢复栈后尾跳原方法。因此静态上没有发现会改变原方法参数或返回值的错误。

响应观察桩只做对象和字段读取、入队，不调用游戏引擎、不写 `CPeaceOffer`/action；帧线程再输出日志。虚表槽位使用 8 字节 `InterlockedExchangePointer` 安装，安装前暂停进程内已有线程并检查目标入口，正常路径满足本次实验的原子替换要求。

原审计发现的回滚缺陷已在本次增量中修复：虚表槽位保护恢复失败时先恢复原槽指针和帧入口字节；帧入口保护恢复失败时先恢复入口字节，再尝试重新开放槽位并恢复原指针。若重新开放槽位本身失败，代码输出 `hook_rollback_incomplete`、`restart_required=true` 并返回 21，不再声称未安装。正常 API 成功路径和可恢复失败路径均未发现新的阻塞性缺陷。

## 逐项检查

### Win64 汇编边界

`bridge_response_stub`（`frame_stub.S:45–80`）入口依次保存 `RFLAGS`、`RAX/RCX/RDX/R8/R9/R10/R11`，再分配 `0x88` 字节；与 7 个 8 字节保存槽合计 `0xc8`，和 `.seh_stackalloc 0xc8` 一致。调用观察函数前的栈满足 16 字节对齐并提供 Windows x64 的 32 字节 shadow space。`XMM0–XMM5` 保存于 shadow space 之后并在回调后恢复。

回调使用原始 `RCX` 作为唯一显式参数；其他原始易失寄存器和 `XMM0–XMM5` 在回调后恢复，原始栈参数未被移动或重写。恢复保存区和栈后以 `jmp *bridge_response_original` 尾跳，原方法看到的入口栈布局保持不变，原方法的返回值也不会被观察桩覆盖。被调用的 C++ 观察函数没有触碰非易失寄存器；桩本身也没有使用非易失寄存器。

这属于静态 ABI 检查；尚未有一个带额外寄存器/栈参数的独立调用夹具，因此“未知签名参数完全等价”的结论仍是代码级结论，不是运行时证明。

### 观察逻辑和队列

`bridge_response_observe`（`probe.cpp:55–77`）先校验对象地址和 action vtable，再读取双方、原始状态、日期、方向、预览标志和金额字段。匹配不到 FRA/ENG 时直接返回。它没有游戏调用、文件 I/O 或 action 写入；字段写入事件槽后用 `InterlockedExchange(...ready,1)` 发布，帧线程用相应的原子读取消费，发布顺序足以避免输出半写事件。

队列容量为 64（`probe.cpp:30–40`）。它是一次性有界队列：索引达到 64 后后续匹配事件全部丢弃，队列不会循环复用。该行为不会越界或覆盖已发布事件，但若用于长时间运行的响应监视，64 个匹配事件后将永久失去后续样本；这应在产品化前明确记录或改为安全的循环队列。观察回调对每次候选调用至少进行数次 `ReadProcessMemory`，若该虚方法调用频繁，仍可能有可见性能开销。

`state_raw` 只是原始字段。当前不能据此写成“接受”“拒绝”，也不能仅凭队列事件推断和平已结算。

### 原子安装、线程暂停和回滚

安装路径先检查响应槽仍为 `base+0x598f00`，再准备 trampoline、patch 和进程内线程句柄。它只枚举当前进程线程，并排除执行安装的远程加载线程（`probe.cpp:405–430`）；暂停已有线程后检查 RIP 不在被覆盖的 20 字节入口内，写入入口 patch 后刷新指令缓存。响应 vtable 槽位随后改为 `bridge_response_stub`，使用 `InterlockedExchangePointer` 做 8 字节交换（`probe.cpp:441–449`）。正常情况下，这是合适的原子槽位替换顺序。

本次增量复核的失败路径位于 `probe.cpp:431–489`：

1. 响应槽位写入成功后，如果槽位保护恢复失败，代码先用原指针覆盖槽位，再恢复帧入口字节，并再次尝试恢复槽位保护；即使第二次保护恢复失败，槽位指针和帧字节也已回滚。
2. 目标入口保护恢复失败时，代码恢复帧入口字节，并在必要时重新开放槽位、恢复原指针；重新开放槽位失败会进入 `hook_rollback_incomplete`/返回 21。
3. 线程暂停、句柄枚举或入口签名检查失败发生在写入前时，不会留下已写 hook；预分配的 trampoline 可能泄漏到进程结束，但不是当前主要风险。
4. 线程快照之后新建的线程不在暂停集合内，理论上留下安装竞争窗口。当前 DLL 只在加载/安装阶段使用，且目标是游戏长期存在的线程，尚未观察到该竞争；它仍是安装模型的边界条件。

因此，正常路径可以继续做只读响应跟踪测试；若日志出现 `hook_rollback_incomplete`，应按实现约定立即重启进程，不能在同一进程重试。除此之外，本次增量没有阻塞性缺陷。
